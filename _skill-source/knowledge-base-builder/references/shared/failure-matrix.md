# 错题本（共享层：出过什么事，现在谁在拦，哪一格只能靠人问）

`core-rules.md` §五「错误转化为系统能力」的第 ④ 条是「无法自动判断的部分加入人工验收清单」。
**这份文件就是那份清单**——在它之前，④ 一直只是一句口号，没有落点。

它不重写规则。规则住在各自的文件里，这里只回答三个问题：过去哪里栽过、现在有没有机器在拦、
**机器拦不住的那一半，复核时该问哪一句**。

## 一、什么时候读

- **触碰成品的收尾验收**——跑完门禁之后、报「完成」之前，扫一遍第四节里跟本次改动沾边的行；
- **全面 review / 巡检**的内容轴与呈现轴；
- **SKILL.md 第 6 步技能自省**：新出的事故该进第三节还是第四节。

日常 A/B 类任务不必通读，按面挑着看。

## 二、用法三条

1. **第四节的问句是拿来问自己的，不是拿来抄进报告的。** 每一句都能用「是/不是」或一个具体
   事实回答；答不上来就是那一处还没验。
2. **不要把第三节的行再人工查一遍。** 那些已经被脚本判死了，人再看一遍是浪费注意力——
   注意力要花在机器原理上抓不住的地方。历史上第 1 层防线抓不住的病类约占一半（core-rules §三）。
3. **出了新事故，先判它该进哪一节**：能写成判据的写脚本进第三节，写不成判据的写成一句问话
   进第四节。**不许两节都不进**——那等于这次事故白出了。

## 五、这张表自己的维护

新事故按 `core-rules.md` §五 走完五件套之后，回到这里补一行：**能写成判据的进第三节**（同时把
脚本挂进 CI），**写不成判据的进第四节**，问句必须是能用「是/不是」或一个具体事实回答的。

第三节的行只增不减——脚本可以合并，但「这类病曾经存在」这件事不删。第四节的行**可以往上升**：
某一天某条终于写得出判据了，就把它挪进第三节并写上是哪个脚本接手的。
