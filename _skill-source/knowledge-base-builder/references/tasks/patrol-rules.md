# 保鲜巡检规则（C 类任务）

C 类不生产内容，只回答一个问题：**库里哪些"事实"可能已经过期了？** AI 领域的时效性事实
（版本号、"当前主流做法"、安全通告）半衰期常常只有几个月；讲义写完不管，一年后就是给读者挖坑。
巡检产出报告、由用户拍板刷新——巡检本身**永远不改任何成品**。

## 触发方式

- 用户一句话："巡检 / 体检 / 保鲜 / 查查哪些过期了 / 知识库维护"。
- 定时任务（节奏按 KB-CONFIG，默认季度一次）。定时任务的 prompt 是全新会话、没有上下文，
  必须自包含，模板（路径从 KB-CONFIG 抄**绝对路径**，别用相对路径）：

  > 对 <知识库根目录绝对路径> 执行保鲜巡检（C 类）：读各模块 MANIFEST.md，
  > 检查时效性事实是否过期，产出巡检报告到 _maintenance/。不要修改任何成品。

- 另有零成本兜底：A/B 类任务第 1 步会顺手扫各模块核实日期（见 SKILL.md），两者互为保险。

## 两级检查（先便宜后贵）

1. **离线筛选（不联网，秒级）**：跑 `_maintenance/check_freshness.py`。**不要手工比日期**——
   每条事实自带节奏（30/90/180 天，见下），有效复查日 = min(复查日, 核实日期 + 节奏天)，
   脚本一次算完全库并按模块列出超期项。它同时是门禁，所以巡检和 CI 用的是同一套判据，
   不会出现「看板绿着而门禁红着」。
   一条都没命中 → 报告直接写"全库新鲜"，结束，**不进第 2 级、不做无差别重查**。
2. **联网抽查（只查被挑中的）**：对每条超期事实联网核实现状，逐条给结论：
   - `仍然成立` —— 回写 MANIFEST 核实日期即可（节奏与等级不变则不动）；
   - `已过时` —— 写明现状与出处，给出"建议刷新"；
   - `拿不准` —— 写明疑点，留给用户判断。

### 三档复核节奏（2026-08-02 起，取代原统一阈值）

档位写在每条事实自己的「节奏」列，**不是全库一个数**——报价一个月就废，Transformer 原理
一年不变，用同一个阈值既拦不住前者又白扰后者。

| 档 | 收什么 |
| --- | --- |
| 30 天 | 价格、配额、模型目录与版本快照、榜单、**路线图与量产进度**、财务与促销口径、消费端积分、可用区 |
| 90 天 | 协议版本、API 与平台能力、安全清单、评测基准、SDK 版本线、开源项目发版节奏，以及**已发布产品的固定技术规格与官方计量口径**（带宽、容量、标称算力、token 计量、配置文件格式） |
| 180 天 | 原理、方法论、稳定架构模式、已定稿标准、论文结论、经验规律 |

**「已发布规格」与「路线图／报价」是两回事**（2026-08-02 首刷教训）：首刷把 NVLink 带宽、
TPU v7 GA 规格、Gemini 视频 token 计量这类**已经定死的数**跟报价、产能预测一起归进 30 天档，
71 条里 22 条属误判、一周内集中到期。分档过热喂出的是「狼来了」——本页末尾那条
「巡检制度死于狼来了」说的就是这件事。定档时先问一句：**这个数是已经发生并固定下来的，
还是还在往前跑的？**

三条配套纪律：

- **节奏是最长间隔，不是等待时间**。出了产品公告、标准换版、来源失效、安全事件或客户现场
  反证，立刻复核并重算，不等日子到。
- **「复查日」只能把复核往前钉，不能往后推**。给一条 30 天档的报价写个明年的复查日，
  就能合法地让它躺一年——那正是这套机制要防的事，故有效复查日取 min。
- **已公告未生效的翻篇单独钉**（协议出了新版但还在兼容期、法规已公布生效日、
  预发布转正）：把「复查日」写成那个已知节点，事实正文里写清「现行是什么、将来换成什么」。
  取证：MCP 规范 2026-07-28 翻篇那一轮，全靠人记着一条待办做的——人记得住一次，
  记不住第十次。

### 等级与边界（同表两列，巡检顺带核）

- **等级** `A` = 一手权威（官方文档／规范／标准／论文原文／官方定价页）；`B` = 可信二手
  （第三方评测、综述、社区统计、**厂商自称的性能或排名**）。`C` 级线索不进成品——
  门禁直接判 FAIL，要么补到 B 以上，要么按「数字要么有核实日期与信源，要么不写」删掉。
  巡检时若发现某条被当成 A 的其实是厂商口径，就地降级。
- **不能外推** 一句话写清「这条**不能**证明什么」。空着即 FAIL：一条没有边界的数字
  在客户现场就是一句过度承诺。它与网页版证据注的「不可外推边界」是同一件事的两面，
  措辞可以不同，含义不许打架。

### 附加呈现轴（离线，顺带跑，2026-07-14 增设）

时效两级检查之外，巡检顺带给全库讲义做一次**呈现契约自检**：跑库内
`_maintenance/audit_pptx.py`（缺失则用技能包 `scripts/audit_pptx.py`，并顺手复制一份进库；
批量跑遇坏文件/锁文件不会中断），报告附一节「呈现体检」：各册 PASS/FAIL 一览 +
系统性色板漂移/章数不一致/每章元素缺失等告警汇总。
只登记不动手——FAIL 项走 B 类修复，历史留痕照旧。人工已裁决的固定噪音（如 v3.8 保留的
补充型同题页对）登记在库内 `_maintenance/audit-exemptions.txt`，audit 输出 [豁免] 行、
不再计告警（v3.11 起；清单是库级文件，随库不随技能包）。呈现专项报告（如
`YYYY-MM-DD-呈现审查报告.md`）与巡检报告同存 `_maintenance/`，同样只增不改。

**门户坏链检查**（呈现轴的一部分）：跑库内 `_maintenance/check_html_links.py`（缺失则用
技能包副本并复制进库），检查全库 HTML（顶层/模块 README、`_prep/` 取用页）的相对链接
是否都指向真实存在的文件——模块改名、文件挪位、深潜指针失效都靠它兜底。坏链列进
「呈现体检」一节。

**页数账实核对**（呈现轴的一部分，v3.9 增设；v3.10 起有固定脚本）：跑
`_maintenance/check_page_ledger.py`（缺失则用技能包 `scripts/check_page_ledger.py` 兜底，
并复制一份进库），自动比对**四面派生页数账**——模块 README「主力成品 NN 页」/ 顶层 README
模块表 `✅（NN 页）`/（`_prep/`）一页纸 `<span class="pg">`/（模块）`MANIFEST.md` 讲义页数——
与讲义**放映序实测**（`ppt/slides/slide[0-9]+.xml` 计数，与 `audit_pptx.py` 报告页数同口径）
是否一致。配图/删页改了页数却漏回刷派生账是系统性漏洞（v3.9 前普遍存在，一册常同时挂三四个
不同页数）。**v4.2 起同一脚本兼查第二根轴「全库总页数」**——各册实测求和 vs 库根 `README.html`／
`README.md`、`_prep/全库一页纸.html`（标题+页脚）、`_prep/MANIFEST.md` 的总数声明；
此前这根轴无覆盖，单模块四账全绿而总数停在旧值是查不出来的。
对不上就登进「呈现体检」，建议动作＝按 `illustration-rules.md` 第八节四面回刷 + 回刷总数轴。
纯离线、秒级。

**库级产物覆盖率**（呈现轴的一部分，2026-07-22 增设）：跑
`_maintenance/check_prep_coverage.py`，两条轴——①`_prep/*.html` 每条深潜链接的模块 ID／
章节 ID 是否在账本里、href 有没有锚点、目标页面里那个锚点是否真的存在；②实战包的模块覆盖率，
零覆盖模块须在 `_prep/coverage-exemptions.txt` 有理由与登记日。取证：2026-07-22 审出 73 条
深潜链接**一条锚点都没有**、两处模块 ID 写错导致某册被算成零覆盖，而这些七道门禁全查不出。
覆盖率表直接抄进报告，便于看「哪一册的新章还没进库级产物」。

**证据五要素抽查**（内容轴的一部分，2026-07-22 增设）：网页版每条证据注（`.ev`）按
`web-rules` §七要绑五要素，其中**不可外推边界**最容易漏——它是「这个数字在什么条件下不成立」，
恰恰是对客最值钱的一句（客户拿你的数字去别的场景翻车算你的）。巡检抽查方式：
`grep -c '不可外推边界' Web-version/*/index.html`，某册为 0 或明显少于其定量结论数即登记。
取证：2026-07-22 实测 84 条证据注里 51 条只有「核实 + 来源」没有边界，该规则此前只在样板册
MCP 上真执行了。

账实类检查（页数账/书单账/坏链/库级产物覆盖率）的账目全集与真源定义见 `library-rules.md`
「派生账登记表」（v3.13）——巡检是登记表的**事后兜底面**，账要在各任务收尾当场回刷。

### 附加书单轴（离线为主，顺带跑，v3.5 增设；v3.10 起有固定脚本）

跑 `_maintenance/check_ebook_ledger.py`（缺失则用技能包 `scripts/check_ebook_ledger.py`
兜底，并复制一份进库），自动做**账实核对**。**v4.3 判据已换**：库不再下载电子书，账不是
"文件在不在"而是"每条资料有没有给出可用的正规渠道链接"——脚本查三件：条目行「获取方式」列
是否含 http(s) 链接、有无本地馆藏残留（`_reference/ebooks`、`✅ 已下载`、指向 .pdf/.zip 的
相对路径）、链接形态是否合法。这步纯离线、秒级。

**链接失效是这根轴现在最主要的风险**（换判据带来的代价，`ebook-rules.md` 已记）：脚本不探活
（404 与限流难分，且巡检要秒级）。故外链探活**可选但建议做**——条目多时只抽查"阅读建议"点名的
高优先条目，以及厂商白皮书类（OpenAI / Anthropic / AWS / Google 那批最易被挪走或下架，
偏偏又是对客最常引用的）；失效只登记建议替换渠道，不当场改书单。结果附报告「书单体检」一节。

## 巡检报告

存 `_maintenance/YYYY-MM-DD-巡检报告.md`，只增不改（和 raw-data 一个脾气：旧报告永不回改，
新巡检出新报告）。固定结构：

```markdown
# 知识库巡检报告 · YYYY-MM-DD

## 总览
| 模块 | 登记事实数 | 超期数 | 本次结论 |
| --- | --- | --- | --- |
| RAG | 5 | 2 | 1 条已过时，建议刷新 rag-hybrid |

## 明细（仅列超期条目）
| 事实 | 章节 ID | 原核实日期 | 现状结论 | 建议 |
| --- | --- | --- | --- | --- |
| …… | rag-hybrid | 2026-07-08 | 已过时：…（出处） | 刷新该章 |

## 建议动作
1. 刷新 RAG 第 7 章（rag-hybrid）：……（预计动到哪些页）
2. 其余"仍然成立"条目已回写核实日期，无需动作。
```

## 巡检之后

- 用户圈定要刷新的范围 → 逐模块走 **B 类更新**（旧版自动进 `raw-data/history/`，
  改完回写 MANIFEST）。
- "仍然成立"的条目直接回写 MANIFEST 的核实日期——这不算改成品，巡检可以自己做。
- 巡检发现的结构问题（如某模块缺 MANIFEST、命名不一致）也写进报告"建议动作"，但同样只建议不动手。

## 节奏建议

**默认季度全量巡检 + 日常顺手体检**（节奏与阈值在 KB-CONFIG 可调），别轻易做成月度：
个人库的变化频率撑不起月度巡检，
噪音会淹没信号，用户会开始忽略报告——巡检制度死于"狼来了"。
