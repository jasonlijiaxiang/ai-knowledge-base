## 一、逐条核实（全部一等信源：项目自己的 GitHub releases）

核实手法：优先读 `https://github.com/<repo>/releases.atom` 原子源——它给的是带时区的 ISO 时间戳，
比 releases 页面上的相对日期（「27 Jul」）更不容易读错年份；再回到 releases 页面确认哪个 tag 被标 Latest、
哪些是 rc / dev 预发布。横评与综述类材料本次一条没用来定版本号。

| SGLang 当前稳定版 | v0.5.15（2026-07-10） | **v0.5.16，2026-07-25** | github.com/sgl-project/sglang/releases（+ atom：v0.5.16 → 2026-07-25T00:13:18Z） |

几个容易踩的坑，记下来给下轮：

- **Dynamo 的 releases 首页会被预发布刷屏**：`v1.4.0-kimi-k3-dev.1`（07-28）、`v1.3.0-glm-5.2-dev.1`（07-21）
  这类 `-<模型>-dev.N` tag 是给单个模型做的开发版，不是稳定线。认 tag 页上的 Latest 标记，别认列表第一条。
- **atom 源的 `<updated>` 不等于发布时间**：Dynamo v1.3.0 的 atom 时间戳是 07-27（release note 后来被编辑过），
  tag 页显示的发布日是 07-22。两者不一致时以 tag 页为准，本册按 07-22 写入。
- **KServe 式的「补丁版比新小版本还晚」**：同类情况在 AIP 册出现（见那册笔记），本册无。
- **AIPerf 之所以一并核**：p91 那句是「引擎与工具版本 ×× 复核」，把日期推到 08-01 就等于替工具也背书，
  所以顺手把它核了才敢改日期。核不动就应该只改「引擎」不动「工具」。

## 三、顺带纠出的一处内部打架（本册两面之外的收获）

讲义 p43 的 SGLang 卡片停在 **v0.5.14（2026-06-26）**，而同一册 p46 的对比表与 MANIFEST 当时都已经是 v0.5.15——

（它不检查同册不同页的版本号是否自洽），只能靠导全文后通读。本次已把两处一并归到 v0.5.16。

**给下轮的建议**：版本号回写时不要只 grep 一个写法。同一个版本号在本册有三种形态——
卡片里的 `v0.5.16（2026-07-25）`、表头里的 `SGLang v0.5.16`、正文里的 `v0.5.13 起…`（历史锚点，不该动）。
按产品名 grep（`SGLang`）比按版本号 grep（`v0.5.15`）更不容易漏。
