## 接进来：数据从各个系统汇到一处

这一段的目标只有一个：把散在 SharePoint、Confluence、共享盘、业务库里的东西，汇到一个后面能反复重跑的地方。再往下的解析、切分、向量化不在这儿——向量库与嵌入的云落点见 RAG 册，合规与数据出境见 Security 册，管线观测见 AI-Ops 册；本段只讲「数据变成可用语料之前」那一截。同一环节给多厂商代表，有开源自建路线的一并列出，不绑死一家。核实日期 2026-08-02，服务形态与预览状态月级在动，报方案前按当期官方文档逐项复核。

| 技术环节 | 代表性云服务（多厂商，不绑一家） | 给客户一句话 |
| --- | --- | --- |
| 落地区：原始件先有个家（对象存储 / 数据湖） | Amazon S3（表格数据可用 S3 Tables 表桶，原生 Apache Iceberg 格式，S3 自动做 compaction、快照管理与无引用文件清理）/ Azure Data Lake Storage（微软文档已统称此名，不再挂 Gen2；它不是独立服务，是在 Blob 存储上打开分层命名空间得到的一组能力）/ Google Cloud Storage / 阿里云 OSS；表格式自建走 Apache Iceberg、Delta Lake | 原始件先落一个不会被人挪走的地方——后面解析换了工具、切分改了参数，都能从这儿重跑，不用回头求业务部门再导一次。 |
| 存量搬家：本地 NAS 与文件服务器的第一次上云 | AWS DataSync（本地端支持 NFS、SMB、HDFS、对象存储；也支持从 Google Cloud Storage、Azure Blob、Azure Files、阿里云 OSS 等他云搬入）/ Google Storage Transfer Service（本地文件系统、HDFS、S3 及 S3 兼容存储、Azure Blob 起点，官方定位为 1TiB 以上的大批量传输）/ 各云同类迁移与离线寄盘服务 | 第一次搬家是一次性工程，跟以后每天的增量同步是两笔钱、两种人力——报价里要拆开写，不然后面加钱就说不清了。 |
| 企业系统连接器：SharePoint / Confluence / 网盘这类 | Amazon Bedrock 知识库现分两类：托管知识库（Managed，七个连接器：S3、Confluence、SharePoint、Google Drive、OneDrive、网页爬取、自定义）/ 自管知识库（连接器页仍维护 S3、Confluence、SharePoint、Salesforce、网页爬取、自定义，其中 SharePoint 官方标注 preview 且只支持 OpenSearch Serverless 向量库）——注意 AWS 两处文档口径不一致，托管对照表把自管一类写成只剩 S3 与自定义，落地前以控制台实际可选项为准；Amazon Q Business 已停止接新客户，同类需求官方指向 Amazon Quick。Azure AI Search 索引器（SharePoint in Microsoft 365 索引器仍在 preview）/ Google Gemini Enterprise 连接器（Confluence Cloud、Jira Cloud、SharePoint、OneDrive、Outlook、ServiceNow、Microsoft Entra ID 等）/ 阿里云百炼数据连接（文件、表格、MySQL、PostgreSQL、PolarDB-X 2.0、语雀、OSS）；开源自建走 Airbyte | 常见的那几个系统，托管平台都有现成连接器，接上就能跑。但要一个个验——同一个平台里，有的连接器是正式版，有的还挂着预览标，还有的整条产品线已经不接新客户了。 |
| 数据库增量：CDC（变更数据捕获） | AWS DMS（读数据库事务日志，支持「全量 + CDC」与「纯 CDC」两种任务）/ Azure Data Factory 变更数据捕获（原生 CDC 连接器为 SAP CDC、Azure SQL Database、SQL Server、Azure SQL 托管实例、Cosmos DB（SQL API 与分析存储）、Snowflake，其余走自增列自动增量抽取；微软已在该页把 Microsoft Fabric 的 Data Factory 标为下一代，新方案要问清客户走哪条）/ Google Datastream（MySQL、Oracle、PostgreSQL、SQL Server、MongoDB、Spanner 均为正式版，Salesforce 亦正式版；落 BigQuery、Cloud Storage 或 Apache Iceberg 表）/ 阿里云 DTS，数据传输服务 Data Transmission Service（数据同步与数据订阅）；开源自建走 Debezium、Apache Flink CDC | 结构化数据要接的话，走数据库日志，别让人写 SQL 定时全量捞——那是拿客户的生产库当抽数机器使。 |
| 权限元数据跟不跟着文档一起进来（ACL 同步） | 三家现在都能做，但机制与成熟度不一样：Amazon Bedrock 托管知识库的 ACL 感知检索（正式版，SharePoint、OneDrive、Google Drive、Confluence 支持预过滤 + 每次查询实时回源复核权限，S3 与自定义连接器靠客户提供的 ACL 配置文件做预过滤，网页爬取不支持；以邮箱为唯一用户标识，两边对不上就静默查不到东西）/ Google Gemini Enterprise 身份同步（identity sync，把用户账号与 ACL 组的对应关系单独同步，跟全量、增量分开排期）/ Azure AI Search 的 SharePoint 索引器 ACL 摄取（preview）；托管连接器不覆盖时，退路仍是按访问级别拆成多个知识库分别授权 | 文档在源系统里谁能看，这层信息要不要一起接进来——今天就得定。等库灌完再补，等于重灌一遍。 |

**顺着追问什么**：这些系统里，哪几个是真要接的？每个系统谁是管理员、给不给账号、租户管理员同不同意授权？文档在源系统里的权限要不要跟着一起进来？检索的时候由谁来认证用户身份，各系统里那个人的邮箱是不是同一个？

**云替你做不了什么**：云能搬、能跟上变更，但有三件事它自己在文档里就写明了不做。一是不认人：托管知识库的权限过滤是按你传进去的身份筛的，官方明写它不认证最终用户、也无法验证这个身份是真的，认证必须在你自己的应用里做，光靠它不构成访问控制。二是不承诺延迟：数据库增量复制官方明写不是实时复制、延迟没有 SLA（服务等级协议），随源库负载与网络波动。三是账号与取舍：哪些系统接、谁批管理员账号与租户授权、哪份文档算数，还是归客户。

   - URL：https://docs.aws.amazon.com/bedrock/latest/userguide/kb-managed-acl.html

## 看得懂：把 PDF、扫描件、表格变成结构化文本

第 2 章已经把开源侧讲透——MinerU、Docling、LlamaParse、Unstructured 各自的甜区与许可。这里补云侧：客户已有云协议时，这一段多半是买不是搭。四家云都能把版面认出来、给一份结构化文本，但认得了哪些文字、一次能吃几页、出来是不是 Markdown，差距比宣传页上大得多。边界声明：切分怎么切、切完怎么嵌入入库，在 RAG 那一节；本段只管到「解析产物落地成一份能切的文本」为止。

| 技术环节 | 代表性云服务（多厂商，不绑一家） | 给客户一句话 |
| --- | --- | --- |
| 版面与表格解析（主力服务） | Azure `prebuilt-layout`（Document Intelligence v4.0，2024-11-30 GA，出文本、表格、选择标记、图窗与章节层级）——品牌已改叫 Azure Document Intelligence in Foundry Tools 并收进 Content Understanding，但官方同时写明「已在生产上跑的，API、终结点、SDK、计费都不变，不需要迁移」/ Google Document AI 版面解析器（Layout Parser，GA，稳定默认版本 pretrained-layout-parser-v1.0-2024-06-03）/ Amazon Textract AnalyzeDocument 的 FeatureTypes：LAYOUT、TABLES、FORMS、QUERIES / 阿里云文档智能「文档解析（大模型版）」；自建走本章开源四强 | 这一步决定表格以后查不查得回来——先拿你们最难的二十份跑一遍，再定用谁。 |
| 认不认得：语言、竖排、手写 | Azure Read/Layout 印刷体覆盖中文简繁（zh-Hans／zh-Hant），手写体 v4.0 覆盖简体中文 / Google Enterprise Document OCR 官方处理器清单写「200 多种语言」，可用 languageHints 给语言提示 / Amazon Textract 官方配额页只列英法德意葡西六种，并明写不支持竖排；Bedrock Data Automation 文档侧同样只列英德西法意葡、同样不支持竖排（中文只出现在它的音频与自定义词表两侧）/ 阿里云文档智能面向中文场景，官方能力页未列语言表 | 中文扫描件在几家云上不是同一件事——先确认这家的文档服务认不认中文、认不认竖排。 |
| 出什么：Markdown 还是一堆坐标 | Azure 加 outputContentFormat=markdown 直接出 Markdown（v4.0 起表格改用 HTML 片段以表达合并单元格与多行表头，选择标记改用 ☒ ☐）/ 阿里云文档解析（大模型版）OutputFormat 可取 markdown，index 给版面阅读顺序、pos 给坐标 / Google 版面解析器直接给带上级标题与表头的 chunk / Textract 给 Block 结构化 JSON，Markdown 要自己拼 | 解析完直接是 Markdown，下游少写一层拼装代码，也就少一处出错的地方。 |
| 抽字段：合同、发票、报关单 | Amazon Bedrock Data Automation（2025-03 GA，蓝图里配字段，异步开分割器可到 3000 页）/ Azure Content Understanding（2025-11-01 API 版本 GA，分析器里配字段；生成部分要自带 Foundry 模型部署，预览期的托管容量已下线）/ Google Document AI Custom Extractor 与 Form Parser（均 GA），但处理器版本各有自己的下线日期，别把版本号写死进方案 / 阿里云文档智能解析的 Key-Value 键值字段抽取 | 要的只是表里那几个字段而不是全文，就不用训模型——配一张字段表先跑通，再谈准确率。 |
| 批量：几十万页怎么灌进去 | Textract 同步 PDF/TIFF 限 1 页、10MB，异步 3000 页、500MB / Bedrock Data Automation 异步开分割器 3000 页、500MB，但控制台入口只到 20 页、200MB，同步档只到 10 页、50MB / Azure prebuilt-layout 单文件 2000 页、S0 档 500MB（F0 免费档 4MB 且只处理前两页）/ Google 版面解析器在线单 PDF 15 页、20MB，批处理 500 页、单文件 1GB / 阿里云文档解析（大模型版）单文件 1.5 万页、150MB（单图 20MB） | 历史存量是一次性批处理任务，按在线接口估时间和预算一定算错。 |
| 兜底：低置信那几页谁看 | 置信度这层有：Textract 每个 Block 带 Confidence（0–100），Azure Content Understanding 文档侧各种抽取方式都给置信度、还能用 estimateSourceAndConfidence 按字段开关以省时省钱 / 但现成的人工复核队列没了：Google 把 Document AI 的 Human-in-the-Loop（人工复核环节）列入官方废弃清单（废弃日 2024-01-16，同批还有 Document AI Warehouse），AWS 在 Amazon A2I（Augmented AI）文档页首写明不再对新客户开放 / 现实做法是拿云上工单系统或标注平台自己拼一条复核队列 | 解析不可能百分之百，先把「谁看低置信那几页」写进验收，别等上线才临时找人。 |

**顺着追问什么**：最难的 20 份长什么样——扫描件、竖排、手写各占多少？历史存量多少页、多久要灌完？解析错了谁复核、每天看得了几页？有没有一批文档根本不能出网？

**云替你做不了什么**：两件是真做不到，不是没配好。一、AWS 这条线读不了中文：Textract 官方配额页只列英法德意葡西六种文字，Bedrock Data Automation 文档侧也是这六种，两份限制表还都明写不支持竖排——中文扫描件、竖排件在 AWS 上没有开关可打，只能换云或走开源自建。二、现成的人工复核队列买不到了：Google 的 Human-in-the-Loop 已进 Document AI 官方废弃清单，AWS 的 Amazon A2I 明写不对新客户开放，新项目这条队列必须自己搭，工期里要留出来。

### 本阶段登记的时效性事实

5. **云侧文档解析主力服务与形态（2026-08-02 快照）：Amazon Textract 走 AnalyzeDocument 的 FeatureTypes，可取 LAYOUT、TABLES、FORMS、QUERIES；Azure 是 prebuilt-layout（Document Intelligence v4.0，2024-11-30 GA，支持 outputContentFormat=markdown，v4.0 起表格改以 HTML 片段表达合并单元格与多行表头），品牌已改成「Azure Document Intelligence in Foundry Tools」并收进 Azure Content Understanding（2025-11-01 API 版本 GA，含面向检索的 prebuilt-documentSearch 分析器），但官方明写「已在生产上跑 Document Intelligence 的，API、终结点、SDK、计费都不变，不需要迁移」；Google 是 Document AI 版面解析器（Layout Parser，GA，稳定默认版本 pretrained-layout-parser-v1.0-2024-06-03，v1.5 与 v1.6 各版本仍标 Release Candidate）；阿里云是文档智能「文档解析（大模型版）」，OutputFormat 可取 markdown。**

## 存得住、查得清：湖仓、目录与血缘

第 7 章讲的三个执行点和越权测试，落到云上就是这一段：数据存成什么表格式、谁在管这份表的元数据、字段是从哪来的、以及同一张表不同的人能看到哪几行哪几列。这一段的取舍和前面几段不一样——解析工具选错了还能换，表格式和目录选错了，换的是数据本身的家。边界声明：向量库与嵌入的云落点见 RAG 册，合规条款见 Security 册，上线后的观测见 AI-Ops 册；本段只管原始数据在变成可用语料之前，存在哪、查不查得清。服务名与形态按 2026-08-02 当日官方文档逐条核过，出方案前按当期文档复核。

| 技术环节 | 代表性云服务（多厂商，不绑一家） | 给客户一句话 |

**云替你做不了什么**：云做不了的是三件写死在文档里的事，不是「没配」：一，Google 明写通过 Iceberg REST 目录端点管理的表不支持行级、列级细粒度访问控制——在这条路上「开放互通」和「细粒度管控」不能同时要（AWS 的联邦 Iceberg 目录反而可以按行/列/单元格授权，所以这不是开放目录的通例，是按家的硬边界，别互相套）；二，列级血缘有官方写死的采集断点：BigQuery 加载作业与例程不采、单个作业超过 1500 条列级链接不采、嵌套字段不支持，断掉的那截没人替你补；三，Lake Formation 数据筛选器只作用于读操作、只能配 SELECT，写入侧的越权它不看，血缘也不承担访问控制。反过来提醒一句：别把「分类分级」算进云做不了——Databricks 的数据分类与 DataWorks 数据保护伞都能自动识别并打敏感标签，云给的是带置信度的候选标签，定分级标准、出越权测试题、认领哪一列算敏感，才是留给你的活。

**顺着追问什么**：四个指标现在谁在看、多久看一次？阈值是打算人定一个数，还是要让它跟着历史走（这决定了云选哪家）？标注是自己招人还是外包，标注员能不能碰生产数据？你们名下有没有已经在用的 Ground Truth——没有的话这条路对新客户是关着的。坏答案有没有人跟到底？
