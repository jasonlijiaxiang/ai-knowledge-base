## 一、事实核实（2026-07-30 联网，官方一手源）

规范**已于 2026-07-28 正式发布**，版本串 `2026-07-28`，上一版 `2025-11-25`。
官方 changelog 给出 **9 项主变更 + 12 项次要变更 + 4 项弃用 + 1 项治理政策**，每项带 SEP 编号。
下面是本次要写进成品的全部硬事实（**逐条对着官方 changelog 抄核，不是记忆**）：

### 1.1 九项主变更（相对 2025-11-25）

| # | 变更 | SEP |
| --- | --- | --- |
| 1 | 删协议级会话与 `Mcp-Session-Id` 头；`tools/list` 等列表端点不再随连接变化；需要跨调用状态的改用**服务端铸造的句柄**当普通工具参数传 | SEP-2567 |
| 2 | 删 `initialize`/`notifications/initialized` 握手；每个请求在 `_meta` 里自带协议版本与客户端能力；版本不匹配返回 `UnsupportedProtocolVersionError` | SEP-2575 |
| 3 | 新增 `server/discover`（服务端 **MUST** 实现）：广告支持的协议版本、能力与身份 | SEP-2575 |
| 4 | 删 HTTP GET 端点与 `resources/subscribe`/`unsubscribe`，换成单条长连 `subscriptions/listen` | SEP-2575 |
| 5 | 删 `ping`、`logging/setLevel`、`notifications/roots/list_changed`；日志级别改为每请求 `_meta` 带 | SEP-2575 |
| 6 | Tasks 移出实验性核心 → 官方扩展 `io.modelcontextprotocol/tasks`；阻塞式 `tasks/result` 改轮询 `tasks/get` + 新增 `tasks/update`，删 `tasks/list` | SEP-2663 |
| 7 | **MRTR（Multi Round-Trip Requests）**取代服务端发起请求（`roots/list`、`sampling/createMessage`、`elicitation/create`）：服务端返回 `input_required`，客户端带 `inputResponses` 重试原请求 | SEP-2322 |
| 8 | 所有结果必带 `resultType`（`complete` / `input_required`）；旧版服务端省略时按 `complete` 处理 | SEP-2322 |
| 9 | 删 SSE 流可恢复与消息重投（`Last-Event-ID`、SSE event ID）；断流即丢在途请求，客户端须用**新请求 ID** 重发 | SEP-2575 |

### 1.2 次要变更里对售前有用的

- `Mcp-Method` / `Mcp-Name` 头成为 Streamable HTTP POST 的**必带**头——网关、限流器、WAF 不用解 JSON 体就能路由（SEP-2243）
- `tools/list` 等五个端点的结果必带 `ttlMs` / `cacheScope`（`public`/`private`），客户端可缓存、共享中间层可判断能否缓存（SEP-2549）
- `tools/list` **SHOULD** 返回确定性顺序——为的是提高 LLM 提示词缓存命中率
- OpenTelemetry trace context 传播约定进 `_meta`（`traceparent`/`tracestate`/`baggage`）（SEP-414）
- 授权三条：授权响应带 `iss` 且客户端 **MUST** 校验（RFC 9207，SEP-2468）；动态客户端注册须指定 `application_type`（SEP-837）；凭据按签发方绑定、**不得跨授权服务器复用**（SEP-2352）
- 错误码：资源未找到 `-32002` → `-32602`；新增错误码分配政策（`-32000`–`-32019` 实现自定义、`-32020`–`-32099` 规范保留）

### 1.3 四项弃用 + 弃用政策

| 弃用项 | 官方给的迁移路子 | SEP |
| --- | --- | --- |
| Roots | 改用工具参数、资源 URI 或服务端配置传目录 | SEP-2577 |
| Sampling | 直接对接大模型厂商 API | SEP-2577 |
| Logging | stdio 写 `stderr`，或用 OpenTelemetry | SEP-2577 |
| HTTP+SSE 传输（2025-03-26 起就已软弃用） | 迁 Streamable HTTP | SEP-2596 |
| OAuth 2.0 动态客户端注册（RFC 7591） | 改用 Client ID Metadata Documents（CIMD），旧机制保留兼容 | PR #2858 |

**治理**：首次有正式的特性生命周期政策——Active / Deprecated / Removed 三态，
**弃用到最早可移除之间至少十二个月**，并设弃用特性登记表（SEP-2596）。

**SDK**：四个 Tier 1（TypeScript、Python、Go、C#）已出支持版本；Rust 为 beta。

## 三、改法

### 3.1 一条取舍：新内容按「内容归属」分散，不堆在第 3 章

用户要的「详细对比」信息量足够写三四页，但**全塞进第 3 章会把该章深度页顶到 8 页**
（技能规则：深度页 2–6 页，核心章取上限）。而且这些内容天然属于不同章：
「协议怎么变」属传输章，「我的 server 要不要改」属生产落地章，「授权加固」属安全章。

所以：**新增 3 页，分落三章，每章深度页正好到上限 6，不越界**。

### 3.2 讲义（内容真源）

**A. 改写 2 页（不增页，换承载）**

| 页 | 现在 | 改成 |
| --- | --- | --- |
| p33 | 「五版脉络」四卡文字，一行带过 | **五版对照表**：版本 × 传输 / 授权 / 状态模型 / 头条特性（§1.4 那张表）。有取舍就该上表，这是换承载不是加内容 |
| p34 | 无状态信息图，写着「本月底转正」「2026-07-28 生效」 | 改为已发布事实；左右对照补上「跨调用状态怎么办」——官方答案是服务端铸造句柄当普通工具参数传 |

**B. 新增 3 页**

| 落点 | 页题（结论式） | 装什么 |
| --- | --- | --- |
| 第 3 章（深度页 5→6） | 「2026-07-28 逐项对照：九项主变更」 | §1.1 九项，每项写「旧版怎么做 → 新版怎么做 → 对你意味着什么」。带 SEP 号（客户要追溯时给得出） |
| 第 5 章 生产落地（深度页 5→6） | 「我的 server 要改什么：弃用清单与十二个月窗口」 | §1.3 四项弃用 + 官方迁移路子 + 十二个月最短窗口 + 四个 Tier 1 SDK 已支持。**这是客户最关心的那一问的正面答案** |
| 第 6 章 安全（深度页 4→5） | 「授权加固三条：签发方校验、注册收口、凭据不串用」 | §1.2 授权三条 + DCR→CIMD，每条写清「防的是什么攻击面」 |

**C. 对练页增题**（标「新增 2026-07-30」）

- 第 3 章 p37：+2 题——「无状态之后长任务怎么办」「我的 server 要立刻改代码吗」（后者是既有题翻面）
- 第 5 章 p57：+1 题——「升级要停机吗、迁移成本多大」
- 第 6 章 p66：+1 题——「新版授权改了哪些、对我们的安全评审有什么影响」

**D. 存量表述翻面**：其余命中页（导览 p2、第 2 章 p19/20/23/24、第 3 章 p30/32/36/38、
第 5 章 p51、第 7 章速查 p69/71、收尾 p73/74/75）把「当前稳定版 2025-11-25」「即将发布」
改为新版已发布、旧版进入兼容期。**结论骨架基本不动**——抽查发现既有答案实质大多没错
（例：那道「要立刻改代码吗」答的是「有兼容期、至少留 12 个月」，与官方逐字吻合），
翻的是版本现势句。

**E. 回刷五处**（ppt-rules 增补一致性清单）：封面章节条（章数不变，7 章）、导览页、
页码连续、总收束页、来源页补三条新信源。

讲义 **75 → 78 页**。改法走 **zip 级最小手术**（禁整包 round-trip），旧版先进 `raw-data/history/`。

### 3.3 网页版（同批落地，两面事实同源）

- **15 处表述回刷**，与讲义逐句对齐。
- 第 3 章对应节增一个**「版本对照」区块**——网页表格比讲义便宜，这里放**全量**：
  九项主变更全表 + 次要变更里对售前有用的六条 + 四项弃用与迁移路子，每行带 SEP 号与官方链接。
  讲义那页是「讲得完的版本」，网页这块是「查得到的版本」，两面**同源不同粒度**。
- 页脚「本册最近改动」与版本徽标由 `build.py` 重跑同步。
- **不新增交互件**：本册已有报文逐字段注释器，再加一个会挤掉主线。

### 3.4 AI-Gateway 与 Agent：只翻面，不扩散

两册合计讲义 6 页 + 网页 18 处。**只把「即将发布 / 届时复核」改成已发布事实**，
规范细节（MRTR、头路由、列表缓存）**不往这两册扩散**——它们会挤掉两册自己的主线。
AI-Gateway 有一处例外值得补一句：`Mcp-Method`/`Mcp-Name` 头路由**正是网关的事**，
建议在它的 MCP 网关章加一句话（不展开）。

**为什么必须一起做**：这是同一条头条事实。只改 MCP 会让三册在同一件事上直接对立——
比现在三册一致地过期更糟（现在至少读者知道该去查）。工作量很小，别单开一批。

### 3.5 记账与账实回刷

- **三册 MANIFEST**：时效性事实改写（2026-07-28 已发布 + 新增「弃用政策十二个月窗口」
  「四个 Tier 1 SDK 已支持」两条）、新的建议复查日、讲义页数（MCP 75→78）、产出 skill 版本。
  AI-Gateway 的建议复查日已过期 7 天（2026-07-23），一并重定。
- **页数账四面**：模块 README、PPT 面总览、`_prep/` 全库一页纸、MANIFEST。
- **全库总页数 1733 → 1736**：库根 README.md / README.html、一页纸标题与页脚、`_prep/MANIFEST.md`

1. `audit_pptx` 19/19 PASS（含 app.xml 一致性、章数一致性、画布越界）；
2. **渲染目检 MCP 册本体**（07-17 画布事故的铁律：不能只看预览册）；
3. 八道门禁 + `build.py --check` + 技能包两检全绿；
4. CI 绿；
5. 页数账两根轴（单册四面、全库总数）一致；
6. 抽验：线上网页版 MCP 页与讲义在**版本串、弃用窗口、SDK 支持**三处口径逐字一致。

## 五、要拿捏的两处

**① 深度不能做成「规范搬运」**。九项主变更逐项对照，重点不是复述规范，而是每项都要答
「对你意味着什么」——这册的读者是要拿它去见客户的，不是去写 SDK 的。
MRTR、`resultType`、错误码这类偏实现的，一句话点到即可，篇幅给无状态、弃用窗口、授权加固。

**② 十二个月窗口是本次最有价值的一条**，但要说准：官方原文是
**deprecation 到最早可 removal 之间至少十二个月**，不是「新版本再管十二个月」。
说岔了会变成给客户的错误承诺。

## 六、不做

- 不重制整册（只动涉及的章页）；不动第 1、4 章。
- 不把规范细节扩散进 AI-Gateway / Agent 的主线。
- 不新增网页交互件。
- 不改其余 16 册。
