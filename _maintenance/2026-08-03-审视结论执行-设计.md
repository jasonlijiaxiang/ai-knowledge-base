## 一、总口径

- **外科手术**：每项只碰该碰的文件。顺手改周边是本库明令禁止的。
- **先立门禁再改内容**：能变成机器判据的先写成门禁（口径同 v8.5「重组前先让门上线」）。
- **不新造账本**：所有新增检查的判据都从既有真源（MANIFEST／gates.yml／源目录）派生，
  不允许出现第五本手写账。
- **门禁全绿 + CI 绿才算完**，收尾按 web-rules §九·五核对门户三处表述。

## 二、逐项口径

### 1. 保鲜负荷（报告第一节）

三个动作，**不含**报告里提过的「到期宽限期」：

| 动作 | 做法 |
| --- | --- |
| 复核 7 天内到期的 23 条 | 联网取证 + 对抗式复核。**只有拿到实际抓取的 URL 与页面原值才回写核实日期**；值变了的进巡检报告、不动成品（patrol-rules 的既有分界）；取不到证的保留到期标记 |
| 巡检节奏对齐 | 定时任务 `kb-quarterly-patrol` 季度 → **月度**。库里最快的事实节奏是 30 天，季度巡检结构上服务不了它 |
| 降低单条复核成本 | 新增 `gen_source_list.py`：从各 MANIFEST 的「来源」列派生 `_maintenance/信源清单.md`（信源 → 挂了哪几条事实 → 最早到期日）。复核按信源批处理，同一个价格页一次看完 |

**刻意不做：到期宽限期。** 报告里提过「到期后 14 天 WARN、之后 FAIL」。不做，理由是
它拿门禁的确定性换执行的方便，而本库反复吃过的亏正是「报表可以一直红着没人看」
（check_freshness 立项动机本身）。宽限期会把硬门退回成软报表。真正的解法是把负荷降下来
（信源清单）和把供给提上去（月度巡检），不是把标准降下来。

**顺带发现，一并处理**：`AI-Infra-Compute`／`AI-Infra-Platform`／`LLM-Inference` 三册
各自登记了同一条成本事实（H100 时租、自建盈亏线、托管 API 单价），来源写「沿用
llm-inference#llminf-production 同源口径」，但**三条各有独立的核实日期与节奏**——
源刷新了派生的不会跟着动，正是 `_prep` 用「引用映射」防的那种双源漂移，只是发生在
MANIFEST 内部。这次给这类行确立写法：来源写 `沿用 <模块>#<章节ID>`，
由 `check_freshness` 校验被引的那条存在、且派生条的有效复查日不晚于源条。

### 2. 生成器源 JSON（报告第四节）

原件找不回来（既不在 git 也不在磁盘）。做法是**从 PPTX 反解**：
`kb_deck_build.py` 渲染是确定性的，可以逆着写一个 `deck_to_json.py`。

验收判据（目标驱动，不靠肉眼）：反解出 JSON → 用 `kb_deck_build.py` 重渲染 →
新册与原册**逐页文本相等**（`kb_deck_text.py` 按放映序导出比对）+ 页数相等 + audit PASS。
三条都过才算 JSON 是忠实的。**重渲染的 pptx 不入库**，原册字节不动——
这次要的是「源可用」，不是「换一份成品」。

配一道门禁 `check_deck_source.py`：MANIFEST 里声明「生成器渲染」的册必须有对应 JSON，
且 JSON 页数 = 讲义放映序页数。

### 3. 门禁清单塌成一份（报告第二节）

`run_all_gates.sh` 成为唯一入口：

- `make_share.py` 的 `GATES` 元组删掉，改成在解压目录里跑 `run_all_gates.sh`。
  分享包若不含某道门禁需要的东西（如技能源目录），**不静默跳过**——
  要么把它带进包，要么在脚本里写明豁免与理由。
- `release-kb.yml` 的 Release 说明改成一行 `bash _maintenance/run_all_gates.sh`。
- `开始使用.html` 的「八道检查」表述随之回正。

### 4. 脚本双写（报告第三节）

方向定为**技能是上游、库是下游拷贝**（与 skill 里「随库复制进 `_maintenance/`」一致）。

- 新增 `check_scripts_sync.py`（判据抄 `check_skill_sync.py` 的逐文件比对，只比交集）。
- 修 `check_css_classes.py` 的漂移：以库内那份（较新，含动态 class 白名单）为准回流技能。
- 回流 4 道门禁 + `run_all_gates.sh`。后者在新库里没有 `gates.yml`，
  自检那段要加存在性守卫，不能因为缺 CI 就报警。

### 5. 数目声明（报告第六节）

- `check_count_claims.py` 扫描面扩到 `README.md`／`CLAUDE.md`／`_prep/*.md`／`*.yml`。
- 新增**硬门禁** `check_module_count.py`：凡出现「N 模块／N 册／N/N」形态的声明，
  N 必须等于 `PPT-version/` 下的实际模块数（枚举口径直接复用 `build.py`，不另立一套）。
  历史叙述（写在「最后更新」「CHANGELOG」「批次记录」里的过去时）豁免，
  判据是所在文件与所在段落，豁免清单显式登记。
- 修报告里列的 10 处。

### 6. SKILL.md 瘦身（报告第七节）

纯搬家，零规则变更：

- 脚本目录（约 5,000 字符）抽成 `references/tools.md`，SKILL.md 留一张两列表。
- `library-rules.md`（20,297 字符）拆成 `library-layout.md`（第 1、4 步：模块模板／命名／
  raw-data／留痕）与 `library-ledgers.md`（第 5 步：派生账／知识地图／顶层索引／
  技能包打包／分享交接），加载矩阵分列「动手前」与「收尾」。
- 搬完做一次**指针体检**：全库对 `library-rules.md` 的引用要么改名、要么留指针，
  一处都不能断（这类搬家最常见的坏处就是引用悬空）。

### 7. 页脚页码（报告第五节）

拍板：**生成器默认不写页脚页码**，与 18 册对齐。理由是少数服从多数之外，
v8.8 错题本已经记过「凭空加一个 p.124 翻到那页像混进了另一份文件」——
分叉的成本是读者侧的观感，不是维护侧的方便。

已生成的两册**不追改**（改成品要走 zip 级手术、还要重排，收益不抵风险），
在 MANIFEST 登记为已知差异。`check_footer_pagenum` 的总结行改成报「N 册带页码、M 册跳过」，
不再让一道覆盖 3/21 的门禁看起来像全库通过。

### 8. `_maintenance/` 分层（报告第八节）

分 `gates/`（CI 与 run_all_gates 跑的）、`tools/`（人手动跑的 `fix_*`／`kb_*`／生成器）、
`onetime/`（日期前缀与 `*_figs.py`）、`reports/`（报告与设计文档）。
四处路径要同步改：`gates.yml`、`run_all_gates.sh`、`make_share.py`、`.claude/settings.json`
的 allow 列表。搬完全库跑一次坏链与死路径扫描。

**风险与取舍**：这是本批唯一一个大面积动路径的改动，且收益是可读性而非正确性。
放在最后做，前面每一项都不依赖它。

### 9. MANIFEST 变更日志外置（报告第十节）

「最后更新」单元格只留「日期 + 一句话」，历史移到各模块
`raw-data/更新记录.md`。**这一项风险最高**——四道门禁（页数账、保鲜、网页章节、
`_prep` 覆盖）都在读 MANIFEST，`fix_page_ledger.py` 更是显式声明「不动最后更新叙述」。
故做法是：搬运脚本只做剪切粘贴，不改一个字；搬完立刻全门禁 + `build.py --check`。

### 10. 版本号 vs 标签（报告第十一节）

CI 加一道**报告型**检查：SKILL.md 的 `metadata.version` 与最新 `skill-v*` 标签不一致时
打 notice。不拦——发不发版是人的决定，机器只负责别让人忘了。
同批把欠的标签补上（v8.9 起）。

## 三、执行顺序与依赖

保鲜复核（联网，最慢）后台先跑；代码改动按下面串行，每步跑一次全门禁：

```
1 生成器源 JSON      ← 独立
2 脚本双写门禁 + 回流 ← 独立
3 门禁清单塌成一份    ← 依赖 2（run_all_gates 要先回流）
4 数目声明扩面 + 修 10 处
5 信源清单 + 巡检节奏
6 页脚页码
7 SKILL.md 瘦身      ← 依赖 1–6（新脚本都要进 tools.md）
8 MANIFEST 日志外置
9 _maintenance 分层   ← 最后，动路径
10 版本标签检查 + 收尾发版
```

## 四、执行中偏离本设计的两处（如实记下）

### 1. 数目声明：没有去扩 `check_count_claims`，而是另立了一道硬门禁

设计里写「`check_count_claims.py` 扫描面扩到 md／yml」。动手时发现**这两类问题不同族**：
那道脚本查的是「标题说三条、底下列了四条」——**声明 vs 紧跟结构**，判据是 HTML 的表格／
卡片／列表结构，搬到 Markdown 上要重写一套结构识别，噪声还大；而报告里实际抓到的 10 处
全是另一类：**模块数、网页覆盖、门禁道数——真值唯一、可计算、过期即错**。

所以改成新立 `check_derived_counts.py`（硬门禁，判据从真源派生），
`check_count_claims` 维持只扫网页、维持报告型。**两道各管一类，比把一道撑成两用干净。**

### 2. `_maintenance/` 分层：只做了 `onetime/` 一层，没做四层

设计里写分 `gates/`／`tools/`／`onetime/`／`reports/` 四层。动手前数了一下代价：
四层要同步改 `gates.yml`、`run_all_gates.sh`、`make_share.py`、`.claude/settings.json`，
外加技能里所有「随库复制进 `_maintenance/`」的表述与几十处文档引用——
**而收益是可读性，不是正确性**（这一点设计里自己就写了）。

于是只做了风险最低、收益最实的那一刀：**28 个一次性件挪进 `_maintenance/onetime/`**，
常设件全部留在顶层不动路径。这一刀换来一条可判定的性质——
**顶层每个 `.py`／`.sh` 都是常设件、都必须在技能源目录里有对应**——
`check_scripts_sync.py` 直接照这条判，不再用文件名正则猜哪个是一次性的
（正则认不出 `agent_ch10_build.py`）。

报告与设计文档留在 `_maintenance/` 顶层：它们有日期前缀、已经能一眼分辨，
而移动会打断 MANIFEST 与 CHANGELOG 里几十处按路径的引用。**剩下三层没做，
不是忘了，是判断收益不抵代价**；哪天顶层再次长到看不清，再动不迟。
