## 一、4 天后 CI 会变红，而下一次自动巡检在 8 周后（最高优先）

`check_freshness.py` 是**硬门禁**，到期即 FAIL。今天 319 条全部在期，但：

| 时间窗 | 到期事实数 |
| --- | --- |
| 已过期 | 0 |
| 7 天内 | **23**（最早 2026-08-07，LLM 第 5 行） |
| 30 天内 | 67 |
| 90 天内 | 208 |

唯一的自动触发是定时任务 `kb-quarterly-patrol`：`0 10 1 1,4,7,10 *`，
上次运行 2026-07-15，**下次 2026-10-01**。

供需对不上，而且不是小数目。按登记节奏算稳态负荷：

```
30 天档 67 条 + 90 天档 208 条 ÷ 3 + 180 天档 44 条 ÷ 6 ≈ 每月 144 条 ≈ 4.8 条/天
```

每条复核 = 一次联网核实 + 回写 MANIFEST +（若数字进了正文）讲义与网页两面回刷。
需求是**连续的月度负荷**，供给是**季度一次的人工巡检**加上按批次爆发的手工提交
（7-24 到 7-29 五天零提交，8-02 一天 20 次）。

后果不是「保鲜看板红着」——保鲜升成门禁之后，红的是 CI 和首页徽章，
而 CLAUDE.md 的纪律是「CI 红了先修，不要往上叠提交」。等于全库停工。
到那时只剩两个逃生口，都是坏的：**不核实就改日期**（门禁腐蚀，正是 patrol-rules
§「复查日只能往前钉」要防的事），或者**删事实**。

**建议**（按代价从小到大）：

1. 巡检节奏对齐最快的事实节奏——季度改月度，或至少给 30 天档单开一个月度触发。
2. 给 30 天档设**总量预算**。67 条 30 天档 = 每月固定 67 次联网核实，这应该是一个
   主动定价的决定，而不是逐条 MANIFEST 累积出来的结果。超预算时的正确动作是
   降档（这条真的每月都会变吗）或降级为「不进正文、只留 MANIFEST」。
3. 到期前给一段**只警告不拦**的宽限（例如到期后 14 天内 WARN、之后 FAIL），
   让爆发式工作节奏有落地空间。这条要配合 2 做，否则只是把炸弹推后两周。

## 二、门禁清单有四份，两份在静默漂移

| 清单 | 道数 | 有没有防漂机制 |
| --- | --- | --- |
| `.github/workflows/gates.yml` | 15 + 1 报告型 | — |
| `_maintenance/run_all_gates.sh` | 15 + 1 报告型 | **有**：末尾数 gates.yml 的 `- name:` 步数，对不上报警 |
| `make_share.py` 的 `GATES` | **9**（含 build --check、技能包结构、死路径扫描） | 无 |
| `release-kb.yml` 给用户的自检片段 | **6**，硬编码在 heredoc 里 | 无 |

`make_share.py` 漏掉的 6 道恰好是内容正确性最相关的那几道：
**保鲜、网页章节契约、正文标签配平、讲义 audit、页脚页码、技能包与源一致**。
它的注释还写着「自检要跑的门禁：全套，不是挑两道」——那句话在只有 8 道门禁的时候是真的。

对外的说法因此也不准：`release-kb.yml` 的 Release 说明写「打包时已解压自检过：
在解出来的那份里把门禁全跑了一遍」，`开始使用.html:53` 写「八道检查全跑一遍」。
整库 zip 的收件人拿到的自检覆盖 9/15，而他最需要验证的「内容有没有过期」那道不在里面。

**建议**：让 `run_all_gates.sh` 成为唯一入口——`make_share` 在解压目录里直接跑它，
Release 说明只印一行 `bash _maintenance/run_all_gates.sh`。四份清单塌成一份，
现成的 gates.yml 自检继续管住剩下那一处。

## 四、生成器建的两册没有源，可复现性反而倒退了

`kb_deck_build.py`（v8.7）的立意与全库一致：产物从源现场生成。但——

AI-Governance（117 页）与 Predictive-AI-MLOps（122 页）的**整册内容 JSON
既不在 git 里，也不在磁盘上**。`2026-08-02-新模块组装.py` 读 `<各组页 JSON>`
写 `<整册 JSON>`，两个都没留；两册的 `raw-data/` 里只有联网核实笔记和网页覆盖矩阵。

于是设计系统一改，这两册和另外 19 册处境完全相同——只能做 zip 级手术。
生成器承诺的「改令牌就重渲染」，唯二能兑现的两册，恰恰兑现不了。
这也让 v8.8 那次「两处版式常量脱离画布」的修复无法回归验证到成品上。

**建议**：把整册 JSON 补进各自 `raw-data/`，并加一条弱门禁——MANIFEST 声明
「生成器渲染」的册必须有对应 JSON，且 JSON 页数 = 讲义放映序页数。

## 五、讲义悄悄分成了两类，而这不是谁决定的

页脚页码：21 册里 **3 册带**（AI-Governance、Predictive-AI-MLOps、PE），18 册不带。
`check_footer_pagenum` 对 18 册打 `[跳过]`，然后整体报 ok。

这不是设计，是漂移。脚本 docstring 还写着「全库 19 册里只有 PE 带页码，
其余册页脚只有模块名与章名，给它们加页码只会多一份要维护的账」——
而生成器**自动写页码**，所以从今往后每一册新生成的讲义都会自动落进「带页码」那一类。
（v8.8 的错题本已经记到了这个症状：「凭空加一个 p.124 翻到那页像混进了另一份文件」，
但记的是插页场景，没有回头看生成器本身正在制造同一个分叉。）

一道为「插页后页码错位」而立的门禁，现在实际覆盖 3/21，且随生成器使用会长期两类并存。

**建议**：拍板一个方向（全库带，或生成器默认关掉页码），并把 `[跳过]`
从静默改成在总结行报「N 册跳过」——一道报 ok 却跳过 86% 的门禁给的是假安心。

`check_count_claims.py` 只扫 `Web-version/*/index.html`，而且是报告型

我逐条核过、排除了合法的历史叙述，现存**活口径过期**如下：

| `CLAUDE.md:3` | 19 模块 | 21 |
| `CLAUDE.md:49` | 九道门禁 | 15 |

`build.py` 已经有现成的模块枚举，口径直接复用，不必新写一套。

## 七、skill 效能：一次 A/B 任务要先读 6.6 万 token 的规则

按 SKILL.md 的加载矩阵实测（字符数，token 按 0.9 估）：

| 任务类型 | 必读字符 | ≈ 输入 token |
| --- | --- | --- |
| Web 面任务 | 75,844 | 68,000 |
| A/B 类（PPT 面） | 73,041 | 66,000 |
| 配图分支 | 47,518 | 43,000 |
| 初始化 / 布局迁移 | 42,176 | 38,000 |
| D 类库级产物 | 38,302 | 34,000 |
| C 类巡检 | 21,487 | 19,000 |

两个具体的削减点，都不需要改任何规则内容：

1. **SKILL.md 的脚本目录该外置。** SKILL.md 16,247 字符，45% 是「详细规则」节，
   而那节里约 5,000 字符是 18 个脚本各 3–8 行的介绍。技能自己在 v4.9 外置 CHANGELOG
   时给的理由是「版本史是按需读的东西，放正文等于每次任务都白载入一遍」——
   同一条理由对脚本目录成立得更强，**它现在比当年那节版本史还大**。
   抽成 `references/tools.md`，SKILL.md 只留一张「什么时候用哪个」两列表。

2. **`library-rules.md` 该按流程步骤拆。** 20,297 字符，是 shared 三件里最大的一件，
   每个 A/B 与 Web 任务都必读；但它装的派生账登记表、知识地图、顶层索引规则、
   技能包打包与验收、分享与交接，**绝大部分只在第 5 步收尾或特定子任务用得上**。
   拆成 `library-layout.md`（第 1、4 步：模块模板／命名／raw-data／留痕）与
   `library-ledgers.md`（第 5 步：派生账／索引／打包／交接），矩阵里分列「动手前」与「收尾」。

两项合计能把 A/B 任务的必读量砍掉约三成，且是纯搬家，零规则变更。

## 八、`_maintenance/` 是个杂物抽屉

105 个文件平铺一层：

| 类别 | 数量 |
| --- | --- |
| 日期前缀的一次性件（设计文档、报告、回流脚本） | 43 |
| `*_figs.py` 配图脚本 | 20 |
| 常驻工具与门禁 | 35 |
| 其它（维护手册、audit 豁免清单、README.txt 等） | 7 |

结果是回答不了「哪些脚本是承重的」。我做了一次引用计数：**14 个 `.py` 在全库任何
md／yml／sh／html 里零引用**——6 个是日期前缀的一次性回流脚本，8 个是 `*_figs.py`。
它们不该和 CI 依赖的门禁躺在同一层。

**建议**：分 `gates/`（CI 与 run_all_gates 跑的）、`tools/`（人手动跑的 `fix_*`／`kb_*`）、
`onetime/`（日期前缀与 `*_figs`）、`reports/`（报告与设计文档）。
代价是一次性改 gates.yml 与 run_all_gates.sh 的路径，之后长期受益。

## 九、信息收集这一面基本是空的

- `_reference/` 现在只有 2 个文件：吸收清单 + 一份方法论抽取稿。清单里登记的
  4 项参考材料（Codex 对照库、两份讲义快照、分享包）**目录都已不在**。
  「结合最新参考材料」这条路由现在**没有活的入口**。
- 事实只能靠巡检时的联网核实进来，而巡检 10 月才跑（回到第一节）。
- MANIFEST 每条事实都登记了「来源」，但**没有按信源组织的一览**。67 条 30 天档
  分散在 21 份 MANIFEST 里，复核时要重新把 URL 一条条捡出来；
  同一个 OpenAI 价格页可能挂着 5 条事实，现在要翻 3 个模块才能凑齐。

**建议**：从现有 MANIFEST 的「来源」列自动生成 `_maintenance/信源清单.md`
（信源 → 挂了哪几条事实 → 最早到期日），复核按信源批处理而不是按模块。
纯派生、零手写，与 `build.py` 一个脾气。这条能把第一节那 144 条/月的实际工作量
压下去不少——真正独立的信源远少于 319。

## 十一、发布流程：机制是对的，纪律掉了

- 技能当前 **v8.9**，最新 `skill-v*` 标签是 **skill-v8.1**——v8.2 到 v8.9 共 8 个版本
  没有 Release。README 的「历次版本：Releases 里的 `skill-v*`，每条带该版改了什么」
  因此对不上；好在主下载链接指的是库内那份 raw `.skill`（有 `check_skill_sync` 盯着，
  确实永远最新），所以只影响想看版本史的人。
- `kb-v*` 最新 2026-08-02，之后有 3 次提交，属正常滞后。
- 两条发布线本身设计得很好：版本号对账、从源现场打包、包结构 + 内容双自检、
  Release 说明从 CHANGELOG 速查表取。**缺的只是「升了版本号就推标签」这一步没有任何提醒。**

**建议**：在 gates.yml 加一道报告型检查——SKILL.md 的 `metadata.version`
与最新 `skill-v*` 标签不一致时打 notice。不拦，只让它在每次 CI 里说一句。

## 做得好、不要动的地方

- **15 道门禁 1.6 秒跑完，零第三方依赖。** 这是整个工程最强的一环，
  本地循环没有任何摩擦，这直接决定了门禁会被真的跑。
- **每个门禁脚本的 docstring 都写了「为什么要有它」+ 取证。** 一眼知道这道门拦的是哪次事故、
  代价多大。这个习惯比门禁本身更值钱——它让新会话接手时不会把门禁当成官僚主义拆掉。
- **`run_all_gates.sh` 末尾数 gates.yml 步数的自检。** 正确的防漂做法。
  问题只是没推广到另外两份清单（第二节）。
- **`failure-matrix` 把「机器已经拦住的」和「只能靠人问的」分开。**
  「划走注意力」这个设计是对的，比一份大而全的检查清单有用。
- **`build.py` 的 BEGIN/END 生成区 + `--check`。** 派生面不手写这条执行得很干净，
  README.md 的模块表被收进生成区尤其正确。
