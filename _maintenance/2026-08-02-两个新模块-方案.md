## 一、Predictive-AI-MLOps（预测式 AI 与 MLOps）

**归层**：工程保障层
**定位**：回答售前现场那句「我们已经有一堆传统模型了，你们这套跟它什么关系」——讲清预测式 AI
怎么把业务问题切成可学的题、特征的时间语义为什么是头号事故源、模型从实验到生产再到再训练的
完整生命周期，以及它和生成式那套栈能共用什么、不能共用什么。

**不负责**（每一格都指名归属，避免重讲）：生成式应用的运营归 AI-Ops；评估方法谱系与判官归
Evaluation；数据管线与向量库归 Data-Engineering；集群调度与 GPU 归 AI-Infra-Platform；
改 LLM 权重的微调归 Fine-tuning；大模型选型与价格归 Model-Landscape；监管条目与法条时点归 Security。

两处合章是挑刺的结论，理由都成立：**训练服务偏差本来就是时间语义那一章的下游**（同一套特征两条
路径），**再训练是七类信号的下游动作**——分开讲会把因果切断。原方案 `3/4×4/5×4/6×3` 的整齐阶梯
被判为「像在分配一个 57 页的预算，不像量出来的内容」，这条批评对。

**全册核心是 `pam-monitoring`**：七类信号——数据质量故障、训练服务偏差、输入漂移、预测漂移、
成熟真值上的性能下降、概念漂移、反馈与选择偏差——看起来都像「模型不行了」，对应动作却完全不同。
「监测到漂移就自动重训」是最常见的错：漂移不等于变差，标签没成熟就重训等于拿噪声追噪声，
上游数据故障时重训会把故障学进模型里。

### 与既有模块划界（挑刺后补了三处）

| 撞哪儿 | 怎么划 |
| --- | --- |
| **AI-Ops 第 7 章 工具格局** | 挑刺发现原方案整个漏了这一章，而 MLflow 已是 AI-Ops 的登记事实。分工写死：LLM 观测/评估平台货架与版本锚点归 AI-Ops，模型注册表语义与预测式监控工具（Evidently / NannyML）归本册 |
| **AI-Ops `ops-drift`** | 同名不同物，最需要互指：那边的漂移没有客观真值（供应商静默换权重、输出漂移），本册的漂移有真值但有标签延迟。两章各自声明「这里说的漂移指哪一种」 |
| **Data-Engineering `de-labeling`** | 原方案漏了最容易撞的一格。那边的标注是人去打的、成本在人力；本册的标签是等出来的、成本在时间——标签成熟期直接决定 POC 周期 |
| **Evaluation** | 原方案把界划在「有没有真值」上，会真的重讲（Evaluation 第 3 章正表里代码判分本来就是第一档）。改划在**对象**上：Evaluation 管 LLM 输出的判分方法与评估集运营，本册管预测式模型在业务约束下的指标与阈值选择（极不平衡、成本不对称、每天只能打 500 个电话这类容量上限） |
| **Security `sec-governance`** | 治理框架组合与法条时点归 Security，本册只讲落到预测式交付物上的那几格：拒绝理由说不说得出、公平性定义之间的不可兼得、模型卡与独立验证 |
| **Model-Landscape `ml-price`** | 「两种 AI 单次成本差着量级」这个论据要引 ML 不抄；预测式那一侧的量级数本册自己登记 |

## 二、AI-Governance（AI 治理、风险与合规）

**归层**：工程保障层
**定位**：把治理讲成一套**一直在跑的决定系统**——某个 AI 用途由谁、依据什么证据，作出批准／
条件批准／例外／暂停／退役的决定，以及什么变化必须触发重新决定。不是一份合规文档。

**不负责**：技术威胁与防护手段、中国备案与标识的具体条目归 Security 第 4–8 章；怎么测归
Evaluation；发布门禁、金丝雀与事故恢复的技术动作归 AI-Ops 第 5–6 章；数据权限执行点与血缘归
Data-Engineering；模型许可证条款归 Model-Landscape。

### 章节（挑刺后：11 章，深度页 47 → 约 51）

| 章节 ID | 标题 | 深度页 |
| --- | --- | --- |

| `gov-risk-tiering` | 组织风险分层与法律分类是两把尺子 | 5 |

**贯穿案例**：招聘筛选 AI 走完整条决策链——同一个模型写职位描述和筛简历必须是两条独立记录，
这一句比罗列框架管用。

### 与 Security 的划界（挑刺后重写，这是本册最要紧的一处）

原方案把 Security 第 7 章说成「只给方位与时间线」，与库内实际不符——Security 讲义 p65 已给出
三者分工（NIST 给方法论 / 欧盟法案给法律底线 / ISO 42001 给体系），p66–p68 还写了「盘资产 →
设门禁 → AI-SPM 监控」的落地三步。所以改成：

- `gov-frameworks` **只保留 Security 确实没有的三件**：① ISO/IEC 42005 与 42006 这两份
  Security 完全没提的纸；② 义务按 provider / deployer 落到谁头上（含 Art.27 FRIA 适用主体）；
  ③「不能证明什么」——42001 审核范围由企业自划，不针对任何单个用途做安全背书。
- Security 的「安全侧治理落地三步」作为威胁防护章的收口**不动**；本册的「盘」升级成
  **按用途登记**（同一模型多用途要拆条、影子 AI 的挖掘来源、登记字段）。

另修正一处串联错挂：`gov-risk-tiering` 原指向 `agent#agent-eval-guardrails`（评估与护栏），
但自主度光谱的原始定义在 `agent#agent-what-why`、爆炸半径在 `security#sec-agentic`——
拆成两条并改准。

### 待核事实（10 条，两处拆分、两处删日期）

- `ISO/IEC 42001 认证生态` 拆两条：市场快照（B/90）留时效表；**「体系认证 ≠ 单个用途批准」
  是不会过期的性质判断**，移出时效表——它是全册最要紧的一句话，但它不随时间变。
- 两条欧盟法案事实**删掉起算时点**，只登记义务分工与适用主体；时点引 Security 已登记条目，
  不两处各记一份。
- `gov-evidence` 原本一条事实都没有，补一条**法定保存年限**（它自己的对练题就问「证据要留多久」，
  这个只能靠年限数字回答）。

## 四、挑刺抓到的最要害一条：23 章无一章带云落点

两册方案合计 23 章，**一章都没有「上云怎么落地」**。

KB-CONFIG 第 13 行把「工作场景挂钩」定为「上云落地：技术环节 → 主流云服务对照」，
ppt-rules 要求「工作场景挂钩每章检查一次，进阶专章尤其不得缺席」。而这个库刚在同一天用一整批
给 12 册网页版补完这件事（34 表 140 行）——新模块开局就欠同一笔账，是说不过去的。

**已并入方案**：Predictive-AI-MLOps 至少 `pam-feature-store` / `pam-lifecycle` /
`pam-monitoring` / `pam-platform` 四章各带一格云落点；AI-Governance 至少 `gov-registry` /
`gov-evidence` / `gov-operating` 三章各带一格。写法按第 3 步统一下来的五列：
**技术环节 / 云能力 / 客户价值 / 该追问客户什么 / 责任边界**；网页版对应立 `#cloud` 小节。

这条也说明了「先给方案再动手」这道门值多少钱——它是在 23 章讲义生成**之前**被抓到的。
