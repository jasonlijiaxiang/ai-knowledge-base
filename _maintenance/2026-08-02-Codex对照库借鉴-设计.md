# Codex 对照库借鉴 · 设计（2026-08-02）

对照对象：`jasonlijiaxiang/myailearning-codex`（public，HEAD `3588cbb`，2026-08-01 推送）。
同一个人、同一个读者画像（售前）、同一批主题，用完全不同的技术栈做出来的第二个 AI 知识库。
本文只回答一件事：**它有什么是我们没有的，哪些该搬，哪些不该搬。**

---

## 一、它是什么

Next.js 应用，21 个模块，纯网页（无 PPT 面、无书单面）。内容不写在 HTML 里，而是写成
结构化 JS 数据（`app/module-briefs-*.mjs` 等），页面从数据渲染。规模对照：

| | 本库 | Codex 库 |
| --- | --- | --- |
| 模块数 | 19 | 21 |
| 客户问答 | 231 道 | 258 道 |
| 时效性事实 | 224 条（散在 19 份 MANIFEST） | 44 条 claims（单一 `knowledge/claims/index.json`，带 schema）|
| 来源登记 | 每册「来源与核实」表 | 单一 `reference-content.mjs`，215 条 URL，全站只此一处可出现外链 |
| 全库术语表 | 无 | 140 条 `terminology.mjs` + `/glossary` |
| 交付面 | 讲义 PPTX + 网页 + 电子书书单 | 仅网页（+ 英文版）|
| 依赖 | Python 标准库 | Node + Next + drizzle + 一套测试 |

它的内容规范写得极细，值得单独指出来的四份文档：
`docs/MODULE-BUILD-STANDARD.md`（怎么建）、`docs/MODULE-QUALITY-GATES.md`（出过什么问题
→ 由什么机制永久拦住）、`docs/CONTENT-DESIGN-STANDARD.md`（语气与构图）、
`docs/CONTENT-MAINTENANCE.md`（事实台账与复核节奏）。

## 二、值得搬的（按杠杆排序）

### 1. 事实生命周期状态机（最该搬的一件）

它的每条易变事实是一条带 schema 的记录，字段：

```
id / claim / scope（适用范围与"不表示什么"）/ sourceIds / evidenceGrade(A|B|C)
/ verifiedAt / reviewBy / reviewCadenceDays(30|90|180) / owner / status
/ announcement{kind, targetClaimId, scheduledFor} / supersedes
```

`status` 四态：`active` 在用 / `watch` 盯着 / `deprecated` / `replaced`（必须关联接替者）。

最关键的是 **`watch` + `announcement`**：**已公告但尚未生效**的标准替换（RC、预告的生效日）
单独建一条 watch 记录，用 `targetClaimId` 指向被影响的现行事实，两条记录的 `reviewBy`
都不得晚于计划日期；等正式版真发布并核实后，才把旧事实转 `replaced`。

对我们的意义：MCP 规范 2026-07-28 翻篇那一轮，我们是**靠人记着**做的（记忆里挂了一条
"2026-08 上旬 MCP 规范翻篇需定点复查"）。它把这件事变成了数据结构。

我们现状的差距：224 条事实里**只有 30 条写了定点复查日**，其余靠 KB-CONFIG 里一个
"巡检阈值 90 天"的统一兜底——价格/配额和架构原理用同一个阈值，明显不对。
也没有证据等级，没有 per-fact 的"不能外推"（我们的不可外推写在**来源**层，不在**事实**层）。

### 2. 超期即阻断发布的硬门禁

它的 `sourceFreshness` 严格解析日期、拒绝未来日期、超期来源直接阻止发布。
我们的 `fresh.html` 保鲜看板是**报表**，不是**门**——看板可以一直红着，门禁照样全绿。

### 3. 「历史问题 → 永久门禁」矩阵

`MODULE-QUALITY-GATES.md` 第 2 节是一张 50 多行的表，每行四列：
**曾出现的症状 / 永久规则 / 工程控制 / 人工复核问什么**。

第四列是精华。因为大量缺陷门禁查不出来（正是我们 CLAUDE.md 写的「门禁全绿 ≠ 对」），
它就把"这一条要靠人看，人该问什么"写死。举两个例子：

- 机制视图 → 人工复核问："读者能否解释*为什么有效、哪里失败、谁负责*，而不是只复述节点名称"
- 按需呈现 → 人工复核问："**删掉这张图会不会更清楚**"

我们的等价物散在 `_maintenance/` 十几份报告 + skill CHANGELOG 里，翻不动，也没有"人该问什么"这一列。

### 4. 深度标尺与理论深度门槛

每个核心知识点固定按五步展开：**定义 → 机制 → 边界 → 判断 → 证据**。
配一条硬判据：**公式只有在会改变售前的架构、选型、风险或验收判断时才展示**，
否则放 Reference。人工复核时对每个公式问一句"它会让售前作出什么不同的判断"。

### 5. 机制 / 判断 / 边界三元组作为常驻字段

它的每个原理卡、每个深挖节点、每个决策点都强制带 `boundary`：

```js
{ name: "注册、发布与运营", mechanism: "…", decision: "…",
  boundary: "技术回滚不能撤销已发生的业务动作，仍需补救、对账和责任流程。" }
```

我们 2026-07-22 做过一次"不可外推边界回刷"，但那是一次性动作，不是常驻结构。

### 6. 决策点的「触发信号」层

```js
{ question: "是否需要建设 Feature Store？",
  signal: "多个模型重复实现特征、线上线下定义不一致，或实时特征访问已成为瓶颈。",
  recommendation: "…", boundary: "Feature Store 不会自动修复错误标签、数据许可或泄漏。" }
```

我们的问答有「短答 / 深一层 / 下一步 / 依据」，但正文的选型处普遍缺 `signal`——
**什么信号出现时才该考虑它**。对售前这是最实用的一层。

### 7. 云服务落点的统一结构（我们自己欠自己的账）

它每个模块都有 `cloudHooks`：**技术环节 / 云能力 / 客户价值 / 该追问客户什么 / 责任边界**。

我们 KB-CONFIG 明写「工作场景挂钩＝上云落地：技术环节 → 主流云服务对照」，
但全库 19 册网页版里只有 9 册提到云服务，且各写各的、无统一结构、没有"该追问什么"。
这是**对照我们自己声明的配置**的欠账，不只是"人家有我们没有"。

### 8. 全库术语表

140 条 `termId` 注册表（中文名 / 英文名 / 缩写 / 一句话说明 / 相关模块，首项为主要归属），
配 `/glossary` 页与门禁（每模块至少 5 个关联术语、2 个主要讲解术语）。
我们的术语解释散在各册正文里，同一个词在不同册的译法一致性靠人记。

### 9. 反套壳：每册先定「主导关系」，再定阅读骨架

它明令禁止「PPT 变网页」——不沿用讲义目录作网页目录，不以"逐页覆盖"为完成标准；
并给每个模块登记一个 `knowledgeView`（如 security→`threat-path`、
llm-inference→`latency-capacity-map`、a2a→`delegated-task-lifecycle`），
`readingProfile` 决定是走标准长页还是聚焦页。

**这条是我们最该照镜子的一条。** RAG 网页版 12 个章节标题与讲义 12 章**逐条 1:1 同序**，
其余各册同理。我们的网页版目前主要是"讲义的另一种排版 + 交互件 + 问答"，
知识**重组**这一步没做。

### 10. 两个内容模块缺口

- **AI Governance（治理 / 风险 / 合规）**——它把治理写成"决策权、责任与证据的运行系统"：
  谁依据什么证据批准 / 限制 / 暂停 / 退役某个用途，什么变化触发重新决定。
  用招聘 AI 走完一条完整治理决策链（登记→分层→影响评估→分配责任→证据包→决定→运行申诉→复审退役）。
  我们只有 Security 第 8 章「中国监管合规」，是**法规条目**视角，不是**运行系统**视角。
- **Predictive AI + MLOps（预测式 AI 与经典 MLOps）**——特征时间语义、point-in-time 正确性、
  训练—服务偏差、七类生产信号（数据质量 / 偏差 / 输入漂移 / 预测漂移 / 真实性能下降 /
  概念漂移 / 反馈选择偏差）。我们的 AI-Ops 册是 GenAIOps，这块**完全空白**。
  售前现场"我们已经有一堆传统模型"这句话没有对应弹药。

### 11. 编码 Agent 雷达

16 个产品（含 Qwen Code / Kimi Code / CodeBuddy / 文心快码 / 通义灵码五个国内面）
× 形态 / 模型策略 / 实现方式 / harness 信号 / 适合谁 / **边界**，
外加 4 个基准（SWE-bench、Terminal-Bench、SWE-ReBench、Harness-Bench）各自的
scope / use / **boundary**。每个产品挂一条 claim，30 天节奏。
我们在 Agent、Model-Landscape、Solution-Patterns 三册有零散提及，没有成体系的选型面。

## 三、我们已经更好、不必搬的

1. **一源两面**。它的 PPT 只是"内容地基"，不是交付物；我们的讲义 PPTX 是真实交付面。
2. **零依赖与可搬运**。我们 Python 标准库 + 静态 HTML，整包拷走即用；
   它是 Next + drizzle + 一套 npm 测试，换机成本高一个量级。
3. **`_prep` 三件套**（实战包 55 题 / 学习路径 / 全库一页纸）——"每日取用"层，它没有等价物。
4. **电子书书单**——它完全没有这一面。
5. **中国面**。我们有 Security 中国监管合规章、Model-Landscape 国内平台格局章、
   Multimodal 国内视频生成；它全库只有 1 条 china claim。
6. **行文**。我们有反 AI 腔纪律与日常词命名（"错题本"）；它的行文更"规范体"、句式偏冷
   （它自己也把"避免反复套用『不是 A，而是 B』『先…再…最后…』"写成规则，说明踩过同一个坑）。
7. **单一账本已经成立**。MANIFEST → `build.py` → `data.js` / README 模块表 / 保鲜看板，
   机制与它的"统一数据源"等价，且更轻。

## 四、明确不搬

- **英文双语版**（它有完整英文 fieldbook + 独立英文编辑规范）：读者画像不需要，工作量巨大。
- **`legacyUndatedQuestionSetSha256`**（用 SHA 冻结历史无日期问答的身份，防止偷渡新题）：
  我们 231 道问答已全部带日期，收益接近零。
- **批次打磨编排**（`module-polish.mjs` 状态机 + 每模块只读 sub-agent）：单人维护，超配。
- **技术栈迁移**：不考虑。

## 五、分批方案

### A 批 · 事实治理升级（建议先做）

把"保鲜"从**报表**变成**门**，并给每条事实配上等级、节奏与边界。

| 项 | 改什么 |
| --- | --- |
| A1 | MANIFEST「时效性事实」表扩列：现 `事实/章节/核实日期/来源` → 增 `等级(A/B/C)`、`节奏(30/90/180)`、`不能外推`；`复查日` 由「核实日 + 节奏」自动算，不再手填 |
| A2 | 增 `状态` 列：`在用 / 盯着 / 已替代`。「已公告未生效」写成 `盯着` 条目，注明指向的现行事实与计划生效日——把 MCP 07-28 那次手工操作固化成写法 |
| A3 | 新增第九道门禁 `check_freshness.py`：任一 `在用` 事实超过其节奏 → FAIL；核实日在未来 → FAIL；`盯着` 条目过了计划生效日未处理 → FAIL。CI 一并跑 |
| A4 | `build.py` 解析新列，`fresh.html` 按节奏分档呈现；KB-CONFIG 的"巡检阈值 90 天"改为三档定义 |
| A5 | skill 的巡检（C 类）章节按三档节奏重写；只核验变化项，无超期则输出"全库新鲜"直接结束 |

**工作量主要在回刷 224 条事实**（19 份 MANIFEST），逐条判等级、定节奏、补边界。
可先用脚本按事实文本特征（含价格/版本号/配额 → 30 天；含协议/API/平台能力 → 90 天；
其余 → 180 天）出一版建议，再人工过一遍。

**验证面**：新门禁自查 + 八道门禁 + `build.py --check` + 保鲜看板目检。

## 七、一个选择时还看不见的设计问题：两面章节不再对齐

**全库重组会打断"一源两面"当前的隐含前提。**

现在 `PPT-version/<模块>/MANIFEST.md` 的「章节清单」既是讲义章节，也直接被网页版当锚点用
（`rag-chunking` 这类 ID 两面共用，`build.py` 据此生成 `data.js`、问答库落点、链接图、串联出边）。
网页版一旦按判断链重组，**讲义章节与网页章节就不再 1:1**，这套 ID 会同时失去两个身份中的一个。

拟定解法（不新开账本，只在唯一真源里加一张映射）：

1. MANIFEST 增一节「网页章节」：`网页章节 ID / 标题 / 承载的讲义章节（可多对多）`。
   讲义章节清单不动——它仍是讲义面的真源。
2. `build.py` 的网页锚点、问答落点、链接图改从「网页章节」取；串联出边允许指向两种 ID。
3. 旧锚点在页面内保留为**隐藏别名**（`<span id="旧ID" hidden>`），深链不断。
4. `check_html_links.py` 扩展：外部曾发布过的锚点必须可达（别名也算）。
5. 新增校验：每个讲义章节至少被一个网页章节承载——**重组可以打散顺序，不能丢内容**。

这条如果不做，`check_page_ledger`、`check_prep_coverage`、问答库和链接图会在重组当天集体失准。
