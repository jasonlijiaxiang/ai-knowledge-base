01数据就绪度是第一风险#de-what-why

库里五处证据都指向同一个坑：POC 三要素的数据坑、企业搜索「连接器是报价大头」、内容生成「产品库是唯一事实源」、坏答案「大半源于脏数据」、「解析质量决定切分质量」——五句话都是果，因在同一处：没人把数据搞就绪。本页就是那个「接住」的动作。对客口径：数据乱不是障碍，「假装不乱」才是。

数据就绪度四问（第一次客户拜访就要问完——答案直接决定排期与报价结构）： ①数据在哪（几个系统、能不能连）②什么格式（PDF 扫描件占比多少）③谁有权（ACL 能不能映射过来）④多久变一次（增量同步节奏）。管线总图四段各对应一个可收费工程件：解析管线（按文档类型分档）→ 清洗同步（连接器按源系统个数）→ 入库（向量库建设）→ 质量运营（运营包按月）。「为什么你们报价里有一块数据工程」的答法：别家不是没有，是藏在里面或做砸了才补——列成明细，每一分钱买了什么看得见，既是收入项也是防烂尾的保险。

数据就绪度评估器

四问的交互版：填客户情况，得到排期量级、报价结构与技术路线建议。判据全部来自本页各节，不新增事实。

02文档解析管线#de-parsing

03连接器与增量同步#de-pipeline

一个连接器 = 五件事：①认证（OAuth/服务账号）②拉取（API 限速与分页）③解析（格式转换）④ACL 映射（权限同步）⑤增量（同步模式）。报价口径：按「源系统 × 五件事」估工作量——SharePoint/Confluence 类成熟源有现成连接器（Airbyte 模式）天级接入；自研系统每个都是一个小项目，那才是大头。

增量同步三模式，按新鲜度需求分级

模式新鲜度代价
轮询差实现最简单——低频源够用
webhook准实时要源系统支持回调 + 丢消息补偿
CDC 变更日志最可靠只有数据库类源才有，工程最重

真实问题是「哪些内容需要多新鲜」——制度文档天级足够，工单类才值得准实时，分级同步省一大笔。

两件没人爱做的脏活

它们决定客户第二个月还信不信这个系统：

去重

同一文档的邮件附件 / 网盘 / IM 转发五个副本——用内容指纹保留权威源。不去重的后果是检索 Top-K 被同一文档霸屏；多数企业第一次实测重复率超过 20%。

失效

离职人员文档、废弃版本——源系统删除 / 归档联动下架。「AI 引用了三年前的报销标准」是信任事故。

同步链路按生产系统运维：断供、限速、权限失效都有告警与补偿重试，每个连接器有健康页——不是脚本跑一次就完。

04向量库选型#de-vectordb

选型第一问是「你已经有什么」：有 Postgres 用 pgvector（生产可用至约 50–100M 向量，ACID、免新系统）、有 ES 就地升级（原生混合检索最成熟）——新引一套系统的运维成本常超过它带来的性能差。五个锚点：pgvector 中小规模首选、Qdrant 过滤检索最强开源（p50 4ms）、Milvus/Zilliz 十亿级分布式、Weaviate/ES 原生混合、托管（Pinecone 等）零运维快速上线。

向量库是「按规模演进」的决策，不是「一步到位」的决策：

迁移纪律

嵌入模型不换向量可搬
换模型必须全量重算——向量空间不兼容。所以嵌入选型要留余量、全量重建做成自动化管线
切换方式双写灰度，新旧库并行跑评估集对比

别为「将来可能的十亿级」提前买复杂度。

性能答法：各家都在毫秒级、量级内差距对多数应用无感——真正拉开差距的是过滤 / 混合检索能力和运维成本，选型看能力匹配不看跑分排名。国产化要求：开源自托管路线全可控（Milvus 是国内团队主导的开源项目）。

选型锚点核实 2026-07-11，来源 2026 向量库对比。不可外推边界：对比表是通用场景下的能力排序，不含客户的过滤条件、并发与运维口径；文中的量级建议是常见生产区间，不是硬上限。

05数据质量与覆盖率#de-quality

把「垃圾进垃圾出」变成四个可度量指标：

解析保真率抽样人工比对，表格重点——异常回炉换解析路线
重复率内容指纹统计——异常修订去重规则
新鲜度各源最后同步时间 vs SLA——异常查连接器健康
覆盖率高频问题的「有答案率」——反向驱动文档补全

全部自动化采集进月报：「数据很乱」变成「重复率 23%、覆盖率 71%」，改进就有了靶子。

但四个指标不是同一种承诺：解析保真率、重复率、新鲜度都在我们管线内，换解析路线、改去重规则、修连接器，数就会动，可以承诺；覆盖率不行——它问的是「客户文档里到底有没有这个答案」，文档里没写的东西，管线做得再好也答不出来。所以覆盖率的正确用法是共担：我们负责把它测出来、给出高频无答案清单，补写是客户团队的活。把覆盖率当承诺签出去，等于替客户的文档质量背书。

坏答案回流：修数据，而不是改提示词

「AI 老答错是不是模型不行」的归因链——经验上八成问题在检索侧，检索问题的大半又在数据侧（解析错 / 文档缺 / 内容过期）：

覆盖率仪表盘的售前故事

高频无答案问题清单 = 客户补文档的优先级表——把「AI 答不上」变成知识治理的入口。补写是客户团队的活，「补什么最值」由数据说话。

运营节奏：日看新鲜度告警、周看坏答案归因、月出四指标报告——与 AI-Ops 运营包同节奏合并交付；停止运营的知识库半年就烂。

三档动作各是谁的活，报价前就要说清：管线内的告警与归因是我们（自动化采集，异常才需要人看）；源系统改版、限速、权限失效由客户 IT 提前知会——连接器是跟着别人的系统走的，这是持续消耗的主要来源；补文档是客户业务团队。三方缺一档，运营就会退回到「出了事再找人」。

06标注与合成数据运营#de-labeling

边界先声明：合成数据配方（种子→扩展→judge 过滤）在 Fine-tuning 网页版——本节管运营与预算。 2026 共识：全人工标注已是少数场景，预算从「雇人标」转向「专家定标准 + 模型产量 + 人工守门」三笔钱：种子人工写（业务专家半天 30–50 条精品，质量标准也在这步定——最贵也最值）、扩量交模型（成本是人工的零头）、验收人工抽检（5–10%，不过线回炉调种子——守住「合成不等于放羊」）。

一份坏例，两条去向

分流先问「是不知道还是不听话」——分流错了钱就白花：

症状本质走哪条线多久见效
不知道知识缺评估集线：修文档 / RAG 更新当天
不听话行为偏训练集线：攒够批次做微调按批次

知识类坏例别硬塞进训练集。评估集线留 10–20% 保留集防应试。

业务专家的时间是最稀缺资源

只用在三件事上——

定标准一次
写种子半天
周审边界样本两小时

这是撬动整个数据飞轮的最小投入。

合成数据「会不会越训越歪」：有纪律就可靠——真实种子打底、judge 过滤、抽检合格率是硬指标（低于七成说明种子或标准要回炉）；纯合成才有坍缩风险。

07治理与权限衔接#de-governance

分工一句话：Security 说「要什么规则」，本页说「规则在管线哪一段执行」——安全评审问到数据层，答案全在三个执行点：①ACL 映射（连接器同步权限元数据、检索时实时过滤、无权限连存在性都不暴露）②采集点脱敏（PII 正则+NER 进库前处理、敏感字段分级——别等检索时再补救）③保留与删除（源系统删除联动下架、遗忘权可执行、审计留痕）。

决策大脑：四类输入 + 一个策略决策

输入例子
主体 + 资源客服 agent 替张三查——主体是「张三经由 agent」，不是 agent 自己
动作 + 上下文同一份文档，客服场景可检索、营销场景不可用于训练
→ 策略引擎给 allow / deny / 附加义务（脱敏、行列过滤、水印、短保留、人工审批）

授权在资源服务端强制执行，模型、查询或客户端都不能自行裁决。

验收与安全团队的三个追问

越权测试集是上线门禁：无权限账号 20 条敏感问题零泄露才放行，调岗 / 离职后重跑。三个追问的标准答案：

追问标准答案
权限多久同步一次随连接器增量；高危变更触发式同步，延迟窗口进 SLA
向量能反推原文吗向量化 ≠ 匿名化，要主动讲——该脱敏照脱敏
删了真删了吗向量库 + 缓存 + 衍生数据三处联动清——评估集里复制过的文档片段最容易被遗忘；「一键遗忘」是设计出来的能力，不是天然就有

与 Security 方案不重复收费：那边定规则与防护体系，这边是规则在数据管线上的施工。

六条验收线 + 血缘：验的是证据链不是组件清单

「有数据湖或向量库」不等于「有可运营的知识底座」——上线前把六条线加越权测试对一遍，每条都要拿得出证据：

验收线要交出什么
生命周期来源到删除可追踪——资产 ID、owner、版本、保留策略
处理重放 / 幂等 / 质量可恢复——checkpoint、测试、backfill 演练
血缘Run / 输入 / 输出与影响可查——事件、目录、责任人（审计记主体与理由，血缘定位派生影响）
检索全文 / 向量 / 过滤有质量证据——查询集、判定集、ACL 测试
服务freshness / p99 / 降级可承诺——端到端 SLO 与演练
治理用途 / 许可 / 删除 / 退出可审计——策略、日志、重建证据

终极判断：任一回答 / 训练 / 评测都能回到数据来源、Run、版本、权限与质量，并能安全回滚、删除或重建。

09上云怎么落地#cloud

前七章讲的是数据底座该怎么建。这一节换个视角：每个环节在云上对应哪个服务、这句话对客户意味着什么、该顺着追问他什么、以及哪些事云替你做不了。按管线阶段排，不按章节排——现场画架构图时是从左到右走的。

同一环节给多厂商代表，不绑死单一供应商。边界：向量库与嵌入的云落点见RAG，合规与数据出境见Security，管线观测见AI-Ops；本节只管到「数据变成可用语料之前」那一截。

接进来：数据从各个系统汇到一处

这一段的目标只有一个：把散在 SharePoint、Confluence、共享盘、业务库里的东西，汇到一个后面能反复重跑的地方。

技术环节代表性云服务（多厂商，非绑定）给客户一句话

顺着追问什么：这些系统里，哪几个是真要接的？每个系统谁是管理员、给不给账号、租户管理员同不同意授权？文档在源系统里的权限要不要跟着一起进来？检索的时候由谁来认证用户身份，各系统里那个人的邮箱是不是同一个？

云替你做不了什么：云能搬、能跟上变更，但有三件事它自己在文档里就写明了不做。一是不认人：托管知识库的权限过滤是按你传进去的身份筛的，官方明写它不认证最终用户、也无法验证这个身份是真的，认证必须在你自己的应用里做，光靠它不构成访问控制。二是不承诺延迟：数据库增量复制官方明写不是实时复制、延迟没有 SLA（服务等级协议），随源库负载与网络波动。三是账号与取舍：哪些系统接、谁批管理员账号与租户授权、哪份文档算数，还是归客户。

看得懂：把 PDF、扫描件、表格变成结构化文本

第 2 章已经把开源侧讲透——MinerU、Docling、LlamaParse、Unstructured 各自的甜区与许可。这里补云侧：客户已有云协议时，这一段多半是买不是搭。四家云都能把版面认出来、给一份结构化文本，但认得了哪些文字、一次能吃几页、出来是不是 Markdown，差距比宣传页上大得多。边界声明：切分怎么切、切完怎么嵌入入库，在 RAG 那一节；本段只管到「解析产物落地成一份能切的文本」为止。

技术环节代表性云服务（多厂商，非绑定）给客户一句话

顺着追问什么：最难的 20 份长什么样——扫描件、竖排、手写各占多少？历史存量多少页、多久要灌完？解析错了谁复核、每天看得了几页？有没有一批文档根本不能出网？

这一段只管「数据变成可用语料之前」的加工与编排：跑批算力、调度骨架、首次全量向量化那一趟。切多大、重叠多少属于切分策略，向量库怎么选、换嵌入模型要付什么代价属于检索侧，见 RAG 册；质量指标体系与运营节奏见本册第 5 章；权限与合规落点见 Security 册——重叠的地方不重讲。

顺着追问什么：全量重建一次多少文档、多久跑一次？增量要天级还是分钟级？源系统删掉一条，下游能不能知道它没了？首次向量化能不能等一晚出结果？

云替你做不了什么：云给的是跑批的机器、调度的骨架和能跑的规则；判断这些规则跑对了没有，它给不了——清洗把 PDF 里的表格洗没了，管线照样全绿。另一件是云够不着的：源系统硬删一条记录又不留删除日志，任何托管管线都无从知道它消失过——这不是没配好，是上游压根没产生这条信息，只能回去改源系统。

存得住、查得清：湖仓、目录与血缘

第 7 章讲的三个执行点和越权测试，落到云上就是这一段：数据存成什么表格式、谁在管这份表的元数据、字段是从哪来的、以及同一张表不同的人能看到哪几行哪几列。这一段的取舍和前面几段不一样——解析工具选错了还能换，表格式和目录选错了，换的是数据本身的家。

行列级管控与脱敏（权限执行点）AWS Lake Formation 数据筛选器（列级/行级/单元格级，只作用于读）/ Databricks Unity Catalog 行过滤器 + 列掩码（SQL 用户定义函数实现；跨多表规模化时官方推荐改用基于治理标签的 ABAC 策略）/ Microsoft Fabric OneLake security 行级 + 列级角色（Lakehouse、Spark 笔记本、SQL 分析端点已正式可用，授权第三方引擎为公共预览）/ BigQuery 行级安全策略 + 列级政策标记（两件事分开配）/ 阿里云 DataWorks 数据保护伞（分类分级 + 静态·动态·引擎层脱敏，脱敏管理需专业版及以上）；自建：Apache Ranger 行过滤 + 列掩码同一张表，不同的人看到不同的行、不同的列——这道卡设在数据层，不要让每个应用各写一遍。

顺着追问什么：表格式定了吗，Iceberg、Delta 还是 Paimon？血缘现在能查到字段级吗，断在哪一段？行列级权限归谁管、卡在数据层还是每个应用各写一遍？

云替你做不了什么：云做不了的是三件写死在文档里的事，不是「没配」：一，Google 明写通过 Iceberg REST 目录端点管理的表不支持行级、列级细粒度访问控制——在这条路上「开放互通」和「细粒度管控」不能同时要（AWS 的联邦 Iceberg 目录反而可以按行/列/单元格授权，所以这不是开放目录的通例，是按家的硬边界，别互相套）；二，列级血缘有官方写死的采集断点：BigQuery 加载作业与例程不采、单个作业超过 1500 条列级链接不采、嵌套字段不支持，断掉的那截没人替你补；三，Lake Formation 数据筛选器只作用于读操作、只能配 SELECT，写入侧的越权它不看，血缘也不承担访问控制。反过来提醒一句：别把「分类分级」算进云做不了——Databricks 的数据分类与 DataWorks 数据保护伞都能自动识别并打敏感标签，云给的是带置信度的候选标签，定分级标准、出越权测试题、认领哪一列算敏感，才是留给你的活。

质量与标注：让语料一直可用

语料建成不等于建好——第 5、6 章管的是它之后怎么不烂掉：四个质量指标怎么自动跑出来、坏例怎么回流、标注与合成的预算怎么花。这一格的云服务分两类：一类把规则和分数跑起来（质量扫描与异常检测），一类把人组织起来标数据（托管标注与预标注）。边界先说清：在线评估怎么抓坏答案在 AI-Ops，合成数据的配方在 Fine-tuning，脱敏与权限规则在 Security，本节只讲数据侧那半段。

技术环节代表性云服务（多厂商，非绑定）给客户一句话
质量规则定义与打分（把「数据很乱」变成一个数）AWS Glue Data Quality（建在开源 DeeQu 上，用 DQDL 规则语言，25+ 内置规则类型，Data Catalog 入口可两步「创建规则 → 推荐规则」，ETL 入口不支持规则推荐）/ Microsoft Purview 统一目录数据质量（完整性、一致性、规范性、准确性、新鲜度、唯一性六个维度的开箱规则 + AI 生成规则 + 自定义规则，2026-03 起 SQL 表达式自定义规则 GA）/ Google Knowledge Catalog 自动数据质量（2026-04-10 前叫 Dataplex Universal Catalog）/ 阿里云 DataWorks 数据质量（内置规则模板库 + 自定义规则，支持单表配置与批量配置）；开源自建 Great Expectations、DeeQu先把「数据很乱」跑成一个分数，改进才有靶子——跑分是自动的，定规则不是。
异常检测与阈值怎么定（这一格几家差得最远）AWS Glue Data Quality 的机器学习异常检测与动态规则（可写 RowCount > avg(last(10)) 这类跟着历史走的阈值，2024-08-07 起正式可用，2026-07-27 起 Data Catalog 入口也能开）/ Microsoft Purview 是人定的固定阈值：规则级与数据资产级可配阈值 2026-05 起正式可用，未达标发邮件别名或通讯组告警，异常状态在「数据质量操作中心」里跟 / Google Knowledge Catalog 走的是先跑数据剖析扫描、由剖析结果推荐规则，分数低于目标分即发通知，不是按历史自动定阈值；开源侧靠自己攒历史统计别把这几家当同一档：只有 AWS 这一格能让阈值跟着你们自己的历史走，其余几家阈值还是人拍的一个数——这个差别开工前就要说清楚。
脏数据阻断（不让坏数据流到下游）阿里云 DataWorks 数据质量：规则与调度任务关联，任务运行成功后自动触发校验，强规则校验失败阻塞下游任务、弱规则只告警 / AWS Glue Data Quality 在 ETL 作业入口跑规则，可定位到没过检的具体记录并隔离（Data Catalog 入口明确不支持定位失败记录）/ 开源自建 Great Expectations 在管线里做校验（Purview 与 Knowledge Catalog 的文档给到的是扫描、评分、告警与操作中心，要卡住下游任务得自己在编排层接）坏数据要在进库前拦下来，进了库再回头修，代价高一个数量级。
托管标注平台（组织人去标那一段）Amazon SageMaker Ground Truth（私有／供应商／Mechanical Turk 三种劳动力；官方文档页顶注记「不再对新客户开放，现有客户照常用，不再引入新功能」，Mechanical Turk 页顶同款注记）/ Azure Machine Learning 数据标注（图像与文本项目，文本支持多分类、多标签、命名实体识别；可从 Azure Marketplace 挂标注供应商，一致性标注为公开预览，单项目上限 50 万文件）/ Google Vertex AI Data Labeling Service 已关停（弃用 2023-06-30、关停 2024-10-03），官方改指 Google Cloud 控制台自助打标或 Marketplace 合作伙伴 / 阿里云 PAI-iTAG（图像、文本、视频、音频与大模型类模板；1.0 自 2026-08-01 起白名单开放并整体进入维护阶段）；开源自建 Label Studio（Apache 2.0）、CVAT、doccano这几年托管标注服务一直在收缩，所以标注标准和标好的数据我们留在你们这边——换工具不换资产。
机器辅助标注与预标注（让人只看拿不准的那部分）SageMaker Ground Truth 自动标注（主动学习，仅支持单标签图像分类、语义分割、边界框目标检测、单标签文本分类四类内置任务，自定义任务与流式作业不支持）/ Azure Machine Learning 机器学习辅助标注（先人工标一批，模型评估出置信度阈值后给出预标签，人工改错；文本 DNN 每例只取前约 128 词）/ 阿里云 iTAG 对部分大模型标注模板（图生文、图文解释等）提供智能标注 / 开源 Label Studio 接 ML 后端做预标注、在线学习与主动学习预标注让人从「从零标」变成「改错」，专家的时间只花在拿不准的那几条上。
质量结果落库、告警与月报（运营跑得下去）AWS Glue Data Quality 结果可写 Amazon S3 或 Data Catalog 的 Apache Iceberg 表（含规则结果、剖析结果、分布结果、逐行结果、观测结果，2026-07-27 起），并接 EventBridge 与 CloudWatch / Microsoft Purview 的质量分数按规则 → 数据资产 → 数据产品 → 治理域逐层汇总，可配邮件别名或通讯组告警 / Google Knowledge Catalog 结果可在 Cloud Logging 里按 data_scan 与 data_quality_scan_rule_result 日志设告警，并出通知报告 / 阿里云 DataWorks 支持质量报告模板与定时发送、多渠道告警订阅四个指标每月自动出一张报告，谁看、多久看一次，开工前就定下来。

顺着追问什么：四个指标现在谁在看、多久看一次？阈值是打算人定一个数，还是要让它跟着历史走（这决定了云选哪家）？标注是自己招人还是外包，标注员能不能碰生产数据？你们名下有没有已经在用的 Ground Truth——没有的话这条路对新客户是关着的。坏答案有没有人跟到底？

云替你做不了什么：云真够不着的是这三条。一，新客户现在买不到公有云的托管标注平台：Ground Truth 与 Mechanical Turk 不再对新客户开放，Google 的标注服务 2024 年就关停了，阿里 iTAG 1.0 从 2026-08-01 起只对白名单——这不是配置问题，是没得开通。二，自动标注只覆盖四类内置任务，自定义任务和流式作业根本不支持，连置信度阈值都由服务预设、不给你调；任务形态一超出这四类，云侧那个开关就是灰的。三，覆盖率云看不见——文档里没写的答案，扫描怎么扫都扫不出来，只能你们自己补。（至于定规则、定阈值、写标注标准，云已经做了一半：推荐规则、AI 生成规则、按历史算阈值都有，但拍板还是人——这算「云做了要你配」，别拿它当云的短板讲。）

10现场高频追问#qa

只收会改变某个决定的问题——会改变技术方案、风险判断、验收方法、对客沟通或下一步行动。

每题标出它加入本题库的日期：2026-07-11 来自讲义首版对练页，2026-07-23 是按客户交锋场景补的三题（数据这块怎么验收 / 能承诺到多少 / 上线后谁维护）。

我们数据很乱，AI 项目是不是做不了？2026-07-11

能做，但顺序要对：先花两三周做数据就绪（解析+清洗+建库），再上模型。乱不是障碍，「假装不乱」才是。

数据坑是 AI 项目烂尾的第一原因——把数据工程列成显性报价明细，既是收入项也是防烂尾的保险。

下一步　用评估器把四问过一遍——答案直接定排期与报价结构；拍脑袋给的工期都是要延期的。

依据　四问与总图

我们全是扫描件和图纸，能处理吗？2026-07-11

能，这正是解析选型的分水岭场景：中文扫描件重默认 MinerU 路线（CJK 版面最强），高价值文档叠 VLM 解析兜底。

表格保真与阅读顺序拉开数量级差距；英文基准分数对 CJK 场景参考有限——自测是唯一可信口径。

下一步　拿客户 20 份最难的文档跑对比测试，用结果定方案——永远不用厂商 demo 定选型。

依据　选型分水岭

接一个系统要多久？数据多久能同步一次？2026-07-11

分两类：主流系统有成熟连接器，天级；自研系统按五件事（认证/拉取/解析/ACL/增量）评估，通常周级。同步按源系统能力分档：webhook 准实时、轮询按小时/天。

真实问题是「哪些内容需要多新鲜」——制度文档天级足够、工单类才值得准实时，分级同步省一大笔。

下一步　拿系统清单当场分类给排期；连接器报价按「源系统 × 五件事」列明细。

依据　五件事与三模式

要不要专门买一套向量数据库？2026-07-11

多半不用急：已有 Postgres 用 pgvector（生产可用到五千万至一亿向量），已有 ES 升级配置就支持混合检索。规模触顶或过滤要求极高时再迁 Qdrant/Milvus。

新引一套系统的运维成本常超性能差；量级内的毫秒差距对多数应用无感——选型看能力匹配度不看跑分。

下一步　方案书附「触顶预案」：监控哪三个指标、什么阈值启动迁移、双写灰度方案——预案本身就是专业度。

依据　按规模演进

AI 老答错，是不是模型不行？2026-07-11

先归因再下结论：经验上八成在检索侧，检索问题的大半又在数据侧——解析错、文档缺、内容过期。坏答案分析一路追到数据层，多数「模型问题」修完数据就好了。

「修数据而不是改提示词」是本册的中心论点——归因占比是对客最有力的论据。

下一步　挑 10 个坏答案做归因练习（检索/解析/缺文档三类占比），把「感觉」变成数据。

依据　坏答案回流

标注要雇多少人？合成数据可靠吗？2026-07-11

尽量不雇：专家半天写种子、模型扩量、人工只抽检 5–10%。合成有纪律就可靠：真实种子打底、judge 过滤、抽检合格率硬指标——纯合成才有坍缩风险。

预算换个花法效果更好；业务专家时间只花在定标准、写种子、审边界三件事上——每周两小时撑起整个标注运营。

下一步　坏例先分流：「不知道」修数据当天见效、「不听话」攒批次微调——分流错了钱白花。

依据　三笔钱与双线

数据向量化之后是不是就安全了？删除能真删干净吗？2026-07-11

向量化 ≠ 匿名化——嵌入在一定条件下能部分反推原文，敏感数据进库前照做脱敏、向量库照做权限隔离。删除要三处联动：向量库、缓存、衍生数据（评估集/训练集候选）一起清，留审计痕。

「一键遗忘」是设计出来的能力——最容易翻车在评估集：坏例回流时复制过的文档片段常被遗忘。

下一步　上线门禁跑越权测试集（20 问零泄露），权限变更后重跑；删除演练把评估集纳入清单。

依据　三个执行点

先做个 POC——数据这块怎么算做完了？拿什么验收？2026-07-23

不看交了哪些组件，看能不能交出证据：「有数据湖、有向量库」不等于「有可运营的知识底座」。把六条验收线逐条对一遍——生命周期、处理、血缘、检索、服务、治理，每条都要拿得出对应的东西（资产 ID 与保留策略、checkpoint 与 backfill 演练、血缘事件与责任人、ACL 测试、端到端 SLO、删除与重建记录），再加越权测试集当上线门禁：无权限账号 20 条敏感问题零泄露才放行。终极判断压成一句：任一回答、训练、评测都能回到数据来源、Run、版本、权限与质量，并能安全回滚、删除或重建。

POC 验收最常见的争议不是技术不行，是「做完了」没有定义——你说交付了，客户觉得还差着。六条线的用处是把「做完」拆成能逐条勾的证据，事前签、不事后争。六条里客户最不设防的是血缘：出事那天要问「这个答案是从哪份文件、哪次 Run 来的」，没血缘就只能靠猜，而那一刻是补不上的。

下一步　POC 启动会上就把六条线当验收清单逐条对：已经有证据的划掉，划不掉的那几条就是本期真实范围——范围写在纸上，比含糊承诺「全都做」更容易签。

依据　六条验收线 + 血缘　·　四个可度量指标

覆盖率、准确率你们能承诺到多少？先给个数。2026-07-23

先把这一问拆开，因为四个指标不是同一种承诺。解析保真率、重复率、新鲜度三个在我们管线内，可以承诺，但阈值要先测基线再定——没测过就报数字是拍脑袋（多数企业第一次实测重复率超过 20%，谁事先猜得到）。覆盖率不能单方面承诺：它问的是「你们文档里到底有没有这个答案」，没写过的东西管线做得再好也答不出来，所以它是共担项——我们负责测出来并给出高频无答案清单，补写是你们的活。至于端到端的答案准不准，那是答案侧的账，指标与阈值口径见 Evaluation 的自建评估。

数据侧最容易被顺口承诺出去的就是覆盖率——它听起来像技术指标，实际是客户文档质量的镜子。签下去等于替对方的文档水平背书，验收时无处可退。当场分清「三个承诺 + 一个共担」，既显得懂行，又把客户从甲方变成一起干活的人。

下一步　POC 第一周先跑一遍四指标基线，把现值当双方的共同起点；高频无答案清单当场给业务方看——那就是他们补文档的优先级表。

依据　四个可度量指标

上线之后这套谁来维护？每个月还要养几个人？2026-07-23

数据侧的持续运营是三档固定动作，不是养一个团队：日看新鲜度告警（自动化采集，异常才需要人看）、周看坏答案归因（挑几条坏例追到数据层）、月出四指标报告。真正吃人力的变数只有一处——连接器是跟着别人的系统走的：源系统改版、限速、权限失效都会打断同步，所以每个连接器要有健康页、告警与补偿重试，做成「告警找人」而不是「人找问题」。分工也一次说清：管线内的告警与归因是我们的活，源系统变更由客户 IT 提前知会，补文档是客户业务团队。这一摊与 AI-Ops 的运营包同节奏合并交付，不重复收费也不重复配人。

客户嘴上问人数，心里怕的是「上线即断供」——同步悄悄停了三个月没人发现。所以把运营写成显性的按月项，比藏进一次性报价里更容易过；停止运营的知识库半年就烂，这句话要你主动说，别等客户第二年自己撞上。

下一步　报价拆成两行：建设一次性 + 运营按月；运营那行与 AI-Ops 运营包合并，别让客户为同一件事付两份钱、配两拨人。

依据　运营节奏　·　同步链路按生产系统运维
